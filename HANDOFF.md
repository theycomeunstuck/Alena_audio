## 1. С чего начать новому агенту

```bash
# всё это работает без БД, эмбеддингов и LLM
python learner-data/tools/validate.py --strict     # 17 карточек, 0 ошибок, 0 предупреждений
python learner-data/tools/selftest.py              # 52 теста
cd TeachCopilot_RAG && pytest tests/ -q            # 137 тестов (2 файла требуют fastapi/эмбеддингов)
python scripts/check_material_coverage.py          # 25 тем учеников, 25 покрыто
python scripts/make_task_card.py zvezdin-artem --prompt-only   # весь 4 этап без модели
```

Если что-то из этого падает — чините это первым, остальное на этом стоит.

**Окружение.** В основном интерпретаторе проекта зависимостей нет (проверено:
`pytest`, `fastapi`, `sentence_transformers`, `psycopg2` не установлены).
Тесты гонялись во временном venv с одним `pytest`; это возможно потому, что
весь новый код либо stdlib-only, либо импортирует тяжёлое лениво. **Не ломайте
это свойство** — оно единственная причина, по которой всё проверяемо здесь и
сейчас.

## 3. Что НЕ проверено — читать первым

1. **Живая модель проверена только облачная (DeepSeek V3), не локальная.**
   Оба пути — генерация карточек и разбор заметок урока — прогнаны на
   `deepseek-chat` через `AI_PROVIDER=deepseek`. Замеры:

   | Редакция | Чистых прогонов |
   |---|---|
   | Промпт v1, без повтора | 8/12 (67%) |
   | Промпт v2 (пример + явные запреты) | 10/12 (83%) |
   | v2 + один повторный запрос с претензией | **16/16 (100%)** |

   **Это оптимистичная оценка.** DeepSeek V3 — большая модель; локальная 4B
   будет ошибаться заметно чаще. Числа означают, что контракт и промпт
   сформулированы понятно, а не что на слабой модели всё будет так же.
   При появлении видеокарты первым делом:
   ```bash
   cd TeachCopilot_RAG && python scripts/check_llm_contract.py --runs 10
   ```
   Если доля чистых прогонов упадёт — правьте
   `prompts/task_designer_prompt.txt` (пример в нём — главный рычаг для слабых
   моделей), а не код: контракт восстанавливается кодом в любом случае.

   **Отправка данных наружу.** Сейчас все 17 учеников вымышленные, поэтому
   облачный прогон безопасен. Для реальных детей облачный провайдер — это уже
   передача персональных данных несовершеннолетних третьей стороне. Правило
   стоит зафиксировать до того, как появятся настоящие карточки.

2. **Сервер не запускался.** `pip install -r requirements.txt` в этом окружении
   не выполнялся, поэтому `uvicorn server:app` и оба новых эндпоинта проверены
   только чтением кода и байт-компиляцией. `tests/test_server_contract.py`
   требует `fastapi` и здесь не запускался.

3. **pgvector-ветка поиска не проверялась.** Нет PostgreSQL. Проверен только
   третий, лексический уровень `retrieval.py` (он же используется по умолчанию,
   когда БД нет).

4. **Пороги правила ЗБР не откалиброваны на живых данных.** 0.85 / 0.30,
   alpha 0.4, максимум падения 0.15 — обоснованное предложение, а не измеренная
   величина. Следствия описаны в ZPD_STAGE4.md; менять их нужно осознанно,
   потому что от них зависит и сложность заданий, и статусы тем.

## 4. Открытые вопросы к владельцу проекта

1. **Старый `pipeline/profile_agent.py` конкурирует с новой моделью данных.**
   Он каждые N сообщений просит LLM выставить оценку 0–100 и пишет её в
   PostgreSQL (`child_knowledge.score`), со своими порогами статусов. Новая
   схема говорит: числовых оценок в карточке нет, освоение считается по уровню
   помощи. Пока живы обе ветки, данные о ребёнке будут расходиться.
   Варианты: (а) переключить profile_agent на наблюдения-уровни помощи и писать
   в JSON-карточку; (б) явно пометить его legacy и не использовать в демо.
   Решение не принято.

2. **Что делать с темой, которую «не проходили, но она явно не по силам».**
   Сейчас такая тема просто не попадает в `learner_model.zpd`, а «не начинали»
   живёт в `knowledge[].status = not_started`. Из трёх карточек
   (`ivanov-ivan`, `belov-timur`, `kuznetsov-maksim`) записи из `zpd.outside`
   поэтому убраны. Если педагогически важно помечать «рано» до всякой
   диагностики — нужен отдельный флаг, это изменение контракта.

3. **Псевдоним нового демо-ученика — «Тёма», а не «Артём»**, потому что
   валидатор требует уникальности псевдонимов, а «Артём» занят карточкой
   `artemov-artem`. Если для демо важно точное совпадение с презентацией —
   нужно решить, какой из двух Артёмов переименовать.

4. **Геймификация не связана с новой моделью.** `mvp.points_ledger` начисляет
   человек, автоматика туда не пишет специально. В концепте описана большая
   система XP/бейджей — она не реализована и в 4 этап не входит.

## 5. Принятые решения (не переигрывать без причины)

1. **Зона выводится из карты компетенций** (пункт 2 концепта), `learner_model.zpd`
   (пункт 3) — производная проекция. Подтверждено владельцем проекта.
2. **Модель не пишет числа.** LLM сообщает факт («хватило наводящего вопроса»),
   число считает код. Это то, что делает оценку воспроизводимой и объяснимой.
   Режим `tutor_confirmed` добавлен по просьбе владельца как второй вариант.
3. **Ответ модели не принимается на веру.** Тема, порядок и число ступеней
   подсказок восстанавливаются кодом; расхождения не глотаются, а печатаются.
4. **Запись в карточку только после полной валидации.** Битое обновление не
   пишется вовсе.
5. **Всё должно работать без сервисов.** Поиск падает до stdlib-уровня,
   `--prompt-only` показывает промпт без модели. Это требование к любому новому
   коду в этих модулях.
6. **Полная карточка ребёнка в промпт не уходит.** Ни `legal_name`, ни журнал,
   ни баллы. Проекции — только `learner_context.py`.

## 6. Известные ограничения

Практические грабли для пользователя вынесены отдельно и разделены на «что
система ловит сама» и «что остаётся на человеке»:
[TeachCopilot_RAG/docs/HOWTO.md → Подводные камни](TeachCopilot_RAG/docs/HOWTO.md#подводные-камни).

Главное, что остаётся на человеке: педагогическая корректность задания
(проверка счёта ловит неверные равенства, но не бессмысленное условие), окно
контекста модели (система предупредит, но ставить 8192 нужно руками) и чтение
предпросмотра перед `--apply`.

Ограничения самой реализации:

1. **Файлы карточек нормализованы** под формат, которым их пишет `card_updater`
   (JSON с отступом 2), поэтому обновление больше не даёт шумных диффов. Новые
   карточки стоит создавать в том же формате.
2. **Защита от повторного применения заметок опирается на дату.** Если
   репетитор применит одни и те же заметки завтра, они применятся снова —
   это осознанно, потому что «то же самое на следующем занятии» бывает.
3. **Лексический поиск — запасной вариант, а не полноценный.** Он ищет по
   совпадению основ слов. Для демо и для 123 задач хватает; на большом банке
   нужен векторный индекс (`scripts/json_rag.py`) или pgvector.
4. **Группа обрабатывается последовательно.** 17 учеников = 17 вызовов модели
   подряд. Параллельности нет.
5. **Один предмет.** Каталог тем — только математика 3–4 класса.

## 7. Что делать дальше (по убыванию пользы)

1. Прогнать `check_llm_contract.py` на реальной модели и починить промпт по
   результатам (см. риск 1).
2. Поднять сервер и проверить оба новых эндпоинта живьём (риск 2).
3. Решить вопрос 4.1 про `profile_agent.py` — пока это единственное место, где
   система может начать врать сама себе.
4. Откалибровать пороги ЗБР на реальных занятиях (риск 4).
5. Интерфейс для репетитора вместо CLI — сейчас всё через командную строку.
6. Векторный индекс вместо лексического поиска: на 123 задачах хватает лексики,
   но с ростом банка понадобится `scripts/json_rag.py` или pgvector.

  docs/HOWTO.md                   инструкция пользователя
