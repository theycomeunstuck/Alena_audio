# RAG_HANDOFF — интеграция `learner-data/` в TeachCopilot_RAG

Документ для владельца `TeachCopilot_RAG`. Описывает, как читать профили учеников
из `learner-data/` и подключать их к `build_system_prompt()`
(`pipeline/prompt_builder.py`). Всё ниже проверено против фактического
поведения инструментов `learner-data/tools/` на момент написания — не
против намерений, а против реального вывода команд.

## 1. Что это

`learner-data/` — ручной, версионируемый в git источник истины по профилям
учеников. Один файл `learners/<learner_id>.json` = один ребёнок. Ведут
репетиторы вручную, без программирования; в файлах только псевдонимы —
никаких реальных имён, контактов, дат рождения, диагнозов, аудио или
транскриптов занятий (см. `learner-data/README.md`, раздел 4).

Важные архитектурные ограничения:

- **Профиль выбирается строго по `learner_id`.** Инструменты открывают ровно
  один файл `learners/<learner_id>.json` — без glob, без поиска по
  подстроке. Чужой профиль не может попасть в вывод даже случайно (см.
  раздел 2 ниже и `learner_common.load_learner`).
- **Это не векторный корпус.** learner-data никогда не индексируется как
  RAG-контент. Учебные материалы (`knowledge_base` в вашей БД, эмбеддинги)
  и персональные профили учеников — два разных источника, которые не
  смешиваются. Подробности запрета — раздел 6.

## 2. Быстрый старт

```
python learner-data/tools/build_context.py <learner_id>
```

Печатает в stdout готовый текстовый блок в том же стиле XML-секций, что
собирает ваш `build_system_prompt()` — конкатенируйте его после базового
системного промпта (`base`/`BASE_SYSTEM_PROMPT`), перед RAG-блоком
`<relevant_material>` или после него, как вам удобнее по месту в пайплайне.

Формат карточки как есть (без рендера в текст) — с `--format json`:

```
python learner-data/tools/build_context.py <learner_id> --format json
```

Дополнительные флаги: `--learners-dir DIR` и `--catalog FILE` (по умолчанию
берутся `learner-data/learners/` и `learner-data/catalog/math_g3_g4.json`
относительно расположения скрипта — не от текущей рабочей директории).

**Коды выхода** (проверено):

| Код | Когда |
|---|---|
| `0` | успех, блок напечатан в stdout |
| `2` | нет такого ученика — `learners/<learner_id>.json` не существует; сообщение в **stderr** |
| `1` | карточка найдена, но битая — невалидный JSON или отсутствуют обязательные ключи верхнего уровня/`profile`/`mvp`; сообщение в **stderr** |

Пример вызова на существующем ученике (`volk-08` — самая насыщенная из 12
примерных карточек; фрагмент реального вывода):

```
$ python learner-data/tools/build_context.py volk-08
<child_safe_profile>
Имя_для_обращения: Волк
Возрастная_группа: 10-11
</child_safe_profile>

<child_learning_profile>
Школьный_уровень: 4 класс
...
Что_уже_знает:
- Многозначные числа: нумерация, разряды и классы [math.g4.numbers.multidigit_numeration]
...
$ echo $?
0
```

Пример на несуществующем ученике (реальный вывод):

```
$ python learner-data/tools/build_context.py no-such-child
Ученик 'no-such-child' не найден: /home/.../learner-data/learners/no-such-child.json
$ echo $?
2
```

Скрипт читает ровно один файл `learners/<learner_id>.json` — это структурная
гарантия в `learner_common.load_learner` (не «мягкое» правило): архитектурно
невозможно, чтобы в выводе оказался чужой профиль.

## 3. Формат текстового блока

`build_context.py` без `--format` рендерит следующие секции (пусто —
секция не печатается вовсе, кроме `<points_balance>`, которая печатается
всегда):

**`<child_safe_profile>`** — знакомо по вашему рендеру из БД:

```
<child_safe_profile>
Имя_для_обращения: Волк
Возрастная_группа: 10-11
</child_safe_profile>
```

**`<child_learning_profile>`** — школьный уровень, язык, стиль объяснения,
темп, автономность, мотивация, визуальность, интересы, плюс три
подсекции по знаниям:

```
Что_уже_знает:
- Многозначные числа: нумерация, разряды и классы [math.g4.numbers.multidigit_numeration]

Что_изучает_сейчас:
- Умножение на однозначное и двузначное число [math.g4.numbers.multiplication_by_1_2_digit]

Типичные_трудности:
- Деление на однозначное и двузначное число [math.g4.numbers.division_by_1_2_digit] — деление столбиком даётся тяжело, часто теряет разряд
```

**`<error_patterns>`** — топ-10 записей `error_patterns[]`, отсортированных
по `count` по убыванию:

```
<error_patterns>
Типичные_ошибки:
- теряет ноль при делении столбиком (предмет: math, тема: Деление на однозначное и двузначное число, повторений: 9)
</error_patterns>
```

Три секции ниже — новые, их не было в вашем текущем DB-рендере:

**`<help_strategies>`** — рабочие приёмы помощи конкретно для этого ребёнка:

```
<help_strategies>
Эффективные_приёмы_помощи:
- сначала нарисовать схему движения стрелками
</help_strategies>
```

**`<session_journal>`** — последние 5 записей журнала (`mvp.journal`),
отсортированы по дате по убыванию:

```
<session_journal>
Последние_наблюдения:
- 2026-07-12: Итог месяца: деление столбиком остаётся приоритетом, площадь составных фигур почти закрыта.
</session_journal>
```

**`<points_balance>`** — вычисленный баланс баллов (сумма `mvp.points_ledger[].points`),
не хранится в файле, печатается всегда, даже при балансе 0:

```
<points_balance>
Баллы: 62
</points_balance>
```

### Отличия от текущего DB-рендера prompt_builder.py

- **Нет `(score: …/100)`.** В MVP-карточках учеников оценок в баллах нет —
  только статус (`confident|learning|needs_support|not_started`). Не
  пытайтесь домысливать score из чего-либо ещё.
- **Названия навыков идут с `[topic_id]`** после человекочитаемого
  названия — например `Многозначные числа: нумерация, разряды и классы
  [math.g4.numbers.multidigit_numeration]`. Название берётся из
  `title_ru` в каталоге по `topic_id`; если `topic_id` не найден в
  каталоге — вместо названия печатается сам id (мягкий фолбэк, ошибка не
  бросается).

## 4. Маппинг JSON → db/schema.sql

Таблица ниже — контракт для **будущего** импортёра в PostgreSQL. Импортёр
не входит в MVP и не существует на момент написания; таблица фиксирует,
как поля карточки лягут в существующие таблицы `db/schema.sql`, когда вы
будете его писать.

| JSON | Таблица.колонка | Примечание |
|---|---|---|
| `pseudonym` | children.name | псевдоним хранится как имя |
| `age_group`, `grade`, `language` | children.* | как есть |
| `profile.*` (5 полей) | child_profiles.* | как есть; `avg_response_time_sec` в MVP отсутствует (nullable) |
| `interests[]` | child_interests.tag | строка на элемент |
| `knowledge[].topic_id` | child_knowledge.subject + .topic | subject = первый сегмент id; topic = title_ru из каталога |
| `knowledge[].status` | child_knowledge.status | **value-map: confident→knows, learning→learning, needs_support→struggling, not_started→строка не создаётся** |
| `knowledge[].notes` | child_knowledge.notes | score в MVP не заполняется |
| `error_patterns[].*` | error_patterns.* | last_seen (date) → timestamptz; topic_id → topic-текст через каталог |
| `mvp.*` | — | импортёр пропускает целиком (`card.pop("mvp")`) |

Сверено построчно с фактическим `db/schema.sql`:

- `children.name/age_group/grade/language` — все четыре колонки существуют
  (`VARCHAR`, `language DEFAULT 'russian'`).
- `child_profiles.explanation_style/pace/autonomy_level/motivation/
  prefers_visual/avg_response_time_sec` — все шесть колонок существуют;
  `avg_response_time_sec REAL` без `NOT NULL`, то есть действительно
  nullable — можно смело оставлять NULL для карточек без этого поля.
- `child_interests.tag` — существует, `UNIQUE (child_id, tag)`.
- `child_knowledge.subject/topic/status/notes` — существуют; комментарий
  в самой колонке `status` в schema.sql буквально гласит
  `'knows' | 'learning' | 'struggling'` — совпадает с value-map выше один
  в один.
- `error_patterns.subject/topic/error_tag/count/last_seen` — существуют;
  `last_seen TIMESTAMPTZ` — конвертация date→timestamptz со стороны
  импортёра нужна, как и указано.

Ключевое: `knowledge[].status == "not_started"` **не** создаёт строку в
`child_knowledge` — отсутствие записи и есть представление «не начинали».
Не пытайтесь заводить строку со статусом-заглушкой.

`profile.score` в БД (`child_knowledge.score SMALLINT`) в MVP не
заполняется никогда — учебных данных с числовой оценкой в карточках нет
(см. раздел 3, «Нет `(score: …/100)`»).

## 5. Таксономия `topic_id`

Грамматика: `math.g<класс>.<раздел>.<тема>[.<навык>]`, например
`math.g4.numbers.division_by_1_2_digit`. Regex (совпадает с
`learner_common.TOPIC_ID_RE` и со схемой):
`^math\.g[34]\.[a-z_]+(\.[a-z0-9_]+){0,2}$`.

- **id неизменяемы.** Тема выводится из оборота через `deprecated: true`
  в каталоге, а не переименованием/удалением id.
- **Мост к без-классовым кодам DB_DESIGN** (например
  `math.geometry.segment`, без сегмента `g<класс>`) — лежит в поле
  `synonyms` каждой записи каталога. Один и тот же без-классовый код
  может встречаться в `synonyms` записей и 3, и 4 класса одновременно —
  дизамбигуация по полю `grade` записи каталога, а не по самому коду.
- Источник истины — `learner-data/catalog/math_g3_g4.json`; `title_ru`
  берётся оттуда для рендера в тексте (раздел 3).

## 6. ЗАПРЕТ на индексацию

**Никогда не направлять `scripts/ingest.py` (ни в одном режиме — `text`,
`pdf`, `json`) на `learner-data/`.**

В частности `--mode json` (функция `ingest_json`, `scripts/ingest.py`,
начиная со строки 272) физически прочитает JSON-файл и для каждого
элемента посчитает эмбеддинг и зальёт строку в `knowledge_base` —
таблицу учебного контента с векторным поиском. Если направить его на
`learners/<id>.json`, персональный профиль ребёнка (пусть и
псевдонимизированный) окажется в векторном индексе учебных материалов и
будет всплывать в поиске `rag.search_knowledge` по семантической
похожести — то есть личные данные ребёнка утекут в контент, который
теоретически виден при любом релевантном запросе, а не только этому
ребёнку.

`learner-data/` — не входной каталог ни для одного режима `ingest.py`.
Профили учеников попадают в промпт ровно двумя путями:

1. Сейчас — только через `learner-data/tools/build_context.py`
   (раздел 2).
2. В будущем — через штатные таблицы `children` / `child_profiles` /
   `child_knowledge` / `child_interests` / `error_patterns`, заполняемые
   отдельным импортёром по маппингу из раздела 4 (импортёр не входит в
   MVP и должен быть написан отдельно — это не `ingest.py`).

## 7. `points_ledger` и геймификация

`mvp.points_ledger[]` — журнал начислений баллов. Форма записи:

```json
{"date": "2026-07-12", "points": 5, "reason": "...", "role": "tutor", "topic_id": "math.g4...."}
```

(`topic_id` — необязательное поле.) Форма сознательно совместима с
событийной моделью `gamification_proposal` (child_id + topic_id +
событие-подобная запись) — то есть при переходе на полноценную
геймификацию строки `points_ledger` можно будет переиграть в события
этой модели почти без трансформации.

Правила:

- **Append-only.** Новые начисления — только добавление строк в конец.
  Исправление уже записанной строки запрещено; ошибочное начисление
  корректируется новой строкой с отрицательным `points`.
- **Баланс всегда вычисляется, никогда не хранится.** `validate.py`
  жёстко следит за этим: любой ключ, содержащий подстроку `balance`
  где-либо в карточке (`_contains_balance_key`), — это `ERROR`. Так что
  ни в одной карточке физически не может появиться закэшированный
  баланс, который разъедется с журналом.
- `build_context.py` считает баланс как `sum(points_ledger[].points)` и
  печатает его в `<points_balance>` при каждом вызове (раздел 3).
- Бейджи, уровни и автоправила начисления — вне `learner-data`; здесь
  только сырой журнал.

## 8. Валидация перед потреблением

Перед тем как использовать данные пакета (и в CI, если будете
подключать), прогоняйте валидатор:

```
python learner-data/tools/validate.py
```

Проверено: на 12 текущих примерных карточках — **exit 0**, `0 errors, 0
warnings`. Exit-коды:

| Код | Когда |
|---|---|
| `0` | всё чисто (по умолчанию предупреждения не считаются ошибкой) |
| `1` | найдены ошибки; либо есть предупреждения и передан `--strict` |
| `2` | папка учеников или файл каталога не найдены (IO-сбой) |

`--strict` — предупреждения (например, «баланс уходит в отрицательные
значения», «дата в будущем», BOM в файле) тоже считаются провалом
(exit 1). На текущих 12 карточках `--strict` тоже даёт exit 0 —
предупреждений нет.
