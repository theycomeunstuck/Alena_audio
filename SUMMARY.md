# Что сделано: 4 этап ЗБР

Ветка `dev`. **Требует проверки на сервере** —
[TeachCopilot_RAG/docs/SERVER_CHECKLIST.md](TeachCopilot_RAG/docs/SERVER_CHECKLIST.md).

Задача была: научить RAG и LLM делать четвёртый, индивидуальный этап урока из
презентации по ЗБР — именную карточку-задание под интересы ребёнка, — и научить
систему заполнять JSON учеников по итогам занятия.

## Главное архитектурное решение

**Модель не решает педагогику и не выставляет числа.**

| Решение | Кто принимает |
|---|---|
| какая тема, какая сложность, сколько ступеней подсказок | правило ЗБР по карте компетенций (код) |
| какая математика допустима в задании | поиск по банку заданий |
| сюжет, формулировки, тексты подсказок | LLM |
| mastery и самостоятельность после урока | код, EMA по уровню помощи |
| что записать в файл карточки | код + валидатор, только после проверки |

Поэтому оценка воспроизводима: на одних и тех же наблюдениях числа получаются
одинаковыми, и репетитору можно объяснить, почему тема попала именно в эту зону.

## Правило ЗБР

Зона выводится из **карты компетенций** (пункт 2 концепта). Блок
`learner_model.zpd` (пункт 3) стал производной проекцией — его перезаписывает
код, руками его больше не поддерживают.

```
mastery ≥ 0.85 и independence ≥ 0.80 → освоено, опоры снимаем
mastery < 0.30                       → пока за пределами ЗБР
иначе                                → в ЗБР: сегодня с опорой, завтра сам
```

Высокая mastery при низкой самостоятельности остаётся **в зоне** — «умеет с
помощью, но не сам» и есть определение ЗБР.

Освоение считается по тому, сколько помощи понадобилось: сам — 1.0, наводящий
вопрос — 0.7, визуальная опора — 0.5, разбирали вместе — 0.25. Следствия:
одна удачная попытка не означает освоения (mastery станет 0.70), освоение
засчитывается после трёх самостоятельных решений подряд, одна неудача не
обнуляет историю (падение ограничено 0.15).

## Что сделано по частям

### Индивидуальная карточка-задание

Сюжет по интересам ребёнка, математика из банка заданий, лестница подсказок
(наводящий вопрос → визуальная опора → частичное решение) отдельным полем: её
открывают по одной ступени и только если ребёнок застрял.

Ответ модели не принимается на веру. Тема, порядок и число ступеней
восстанавливаются кодом, а расхождения не глотаются, а печатаются репетитору.
Дополнительно проверяется то, что по форме не видно:

- **арифметика в тексте** — «8 · 5 = 45» не сходится. Проверка осторожная: не
  трогает перевод единиц, деление с остатком, задания «найди ошибку». На 123
  задачах банка ноль ложных срабатываний;
- **персонализация** — сюжет обязан опираться на интересы, и не только во
  вступлении, но и в самих заданиях;
- **дословное копирование** материала вместо переформулировки под сюжет.

Печатная форма: сначала все детские карточки, потом листы для взрослого с
ответами и подсказками — стопку не нужно разбирать вручную.

### Итоги урока → JSON

Репетитор пишет как говорит: «Тёма начертил луч после наводящего вопроса, но
опять поставил вторую точку». Модель раскладывает это на факты, код превращает
факты в числа, репетитор смотрит дифф и подтверждает.

- одна заметка на всю группу; большие группы автоматически бьются на запросы по
  5 учеников — иначе модель путает детей местами и промпт не влезает в контекст;
- модель получает ростер с допустимыми темами и уже известными формулировками
  ошибок, поэтому не выдумывает темы и не заводит дубли;
- `--interactive` проходит по пунктам разбора: принять или отклонить каждый;
- повторное применение тех же заметок за день не сдвинет оценку второй раз;
- перед записью сохраняется резервная копия карточки (последние 10 версий);
- запись только после полной валидации: битое обновление не пишется вовсе.

### Новый ученик из описания текстом

«Миша, 4 класс, любит динозавров, деление столбиком не идёт — теряет ноль» →
готовый черновик карточки с темами, статусами, ошибками и учебной целью.
Раньше это заводили руками из шаблона, где половина полей обязательные.

### Банк заданий

Было: ученики стоят на 25 темах, материал есть для трёх. Для 15 из 17 карточек
задание собиралось без опоры на программу.

Стало: 123 задачи с разбором, все 25 тем закрыты. В каждой теме есть задача на
её типичную ошибку из профилей учеников. Разрыв виден одной командой и
закреплён тестом, чтобы не отрос обратно.

### Группы и журнал занятий

`learner-data/groups/<id>.json` — состав группы, флаг `--group` вместо
перечисления идентификаторов. `mvp.lessons` — дата, темы, длительность занятия
(пункт 4 концепта); поле необязательное, старые карточки остались валидными.

## Проверено на живой модели

Промпты отлажены не на догадках, а на прогонах через DeepSeek. Это сразу нашло
два дефекта, невидимых на подставной модели: задания копировались из банка
дословно, а сюжет жил только во вступлении.

| Редакция | Чистых прогонов |
|---|---|
| исходный промпт | 8/12 (67%) |
| + пример готовой карточки и явные запреты | 10/12 (83%) |
| + повторный запрос с конкретной претензией | **16/16 (100%)** |

**Оценка оптимистичная:** DeepSeek V3 крупнее того, что поедет локально. Числа
означают, что контракт сформулирован понятно, а не что на 4B будет так же.
Перезамерить на своей модели: `scripts/check_llm_contract.py --runs 10`.

Кроме этого: 137 тестов pytest, 52 теста learner-data, валидация 17 карточек без
ошибок и предупреждений. Всё это работает без БД, без эмбеддингов и без LLM —
модель подменяется фейком, поиск падает на лексический уровень.

## Что требует проверки и решения

Полный список с командами — [SERVER_CHECKLIST.md](TeachCopilot_RAG/docs/SERVER_CHECKLIST.md).
Главное:

1. **Сервер и два новых эндпоинта ни разу не запускались** — здесь не было
   установлено `fastapi`. Проверены только чтением кода.
2. **pgvector-ветка поиска не проверялась** — не было PostgreSQL. Работал
   лексический запасной уровень.
3. **Локальная модель** будет ошибаться чаще облачной. Нужен контекст от 8192.
4. **Педагогическую корректность заданий проверяет человек.** Код ловит неверный
   счёт, но не бессмысленное условие. Карточку читаем перед выдачей ребёнку.
5. **`pipeline/profile_agent.py`** пишет в PostgreSQL свои оценки 0–100 по своим
   порогам — это второй, конкурирующий с ЗБР источник правды. Пока живы обе
   ветки, данные о ребёнке будут расходиться. Решение не принято.
