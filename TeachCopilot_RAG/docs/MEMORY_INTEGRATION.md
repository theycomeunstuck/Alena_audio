# Память в локальном TeachCopilot

Память использует существующие аккаунты, права на ученика и PostgreSQL. Учебные сессии отделены от сессий авторизации. Рабочий метод до содержательного просмотра исследования человеком – `tail`. `profile_only`, `summary` и `structured` доступны для демонстрационного сравнения.

Источники сохраняются дословно с автором и временем. Реплика ассистента хранится в диалоге, но исключается из доказательств учебного результата. Модельные записи и рекомендации остаются черновиками. Подтверждение версии памяти не записывает компетенции.

## Запуск

Из каталога `TeachCopilot_RAG`, после установки локальных зависимостей и настройки `.local.env`:

```powershell
.venv-local/Scripts/python.exe scripts/manage_local.py migrate
.venv-local/Scripts/python.exe -m uvicorn local_app.api:app --host 127.0.0.1 --port 8000
```

Worker запускается отдельным процессом с теми же настройками БД и локальной Ollama:

```powershell
.venv-local/Scripts/python.exe scripts/memory_worker.py
```

Для конечного пакета используйте `scripts/memory_worker.py --max-jobs 40`. Процесс завершится после сорока заданий или при пустой доступной очереди. Он не повторяет неудачную генерацию. Повторные запуски обрабатывают оставшиеся задания, а не перезаписывают завершённые результаты.

Исследовательский код и приложение используют `research_memory.methods.Memory`, одинаковый бюджет выбранной памяти 4000 символов и контракты ссылок. Писатель получает полный вход без скрытого сокращения. Проверка бюджета включает схему и явно обозначенный эвристический запас. При превышении бюджета сохраняется отказ. Приложение продолжает использовать последнюю готовую версию с отметкой актуальности; при наличии такой версии подготовка рекомендации может продолжиться с явной отметкой `stale` и диагностикой обновления.

## API

Все запросы требуют существующий Bearer-сеанс. Доступ проверяется сервером по назначению ученика аккаунту.

| Операция | Запрос | Результат |
|---|---|---|
| Следующий шаг | `POST /learners/{id}/next-step` с `topic_id`, необязательными `method` и `expected_revision` | `202`, `job_id` |
| Задание очереди | `GET /memory/jobs/{id}` | `queued`, `running`, `completed`, `failed` или `unknown_outcome`; результат и диагностика доступны преподавателю |
| История памяти | `GET /learners/{id}/memory?topic_id=...` | Источники, версии, ревизии и актуальность; только преподавателю |
| Подтвердить память | `POST /learners/{id}/memory/versions/{version_id}/confirm` с `expected_revision` | Атомарная проверка ревизий ученика и источников; только преподавателю |
| Начать занятие | `POST /learners/{id}/learning-sessions` с `topic_id` и необязательным `client_session_id` | `201`, `learning_session_id` |
| Завершить занятие | `POST /learning-sessions/{id}/complete` | `202`, однократная постановка обновления памяти |
| Создать задание по рекомендации | `POST /task/design` с необязательным `next_step_id` | Проверка ученика, темы, ревизий карточки и источников |

Рекомендация содержит `action`, `reason`, `evidence_turn_ids`, `unknowns`, `review_required: true`, раскрываемые `sources` и использованный контекст. Пустой `unknowns` сам по себе не обозначает ошибку. Устаревшая память обозначается отдельно от неизвестных условий учебной работы.

В `POST /v1/chat/completions` можно добавить `learning_session_id` и `client_message_id`. Сервер принимает последнюю пользовательскую реплику, а остальной диалог собирает из сохранённых источников. Повторный идентификатор сообщения с тем же текстом возвращает сохранённый ответ; другой текст с тем же идентификатором отклоняется. Чат использует только подтверждённую долговременную память и текущий диалог. Старый API без учебной сессии сохраняет прежний формат диалога и проходит через ту же устойчивую очередь, но не создаёт долговременные источники.

Предложение обновления после занятия показывает буквальный источник памяти рядом с изменениями карточки. Подтверждение атомарно сохраняет карточки, источники и задания обновления. Повторное подтверждение возвращает прежний результат. Групповая заметка явно сохраняет неизвестное авторство отдельных результатов.

## Очередь и сбои

Очередь допускает до 40 ожидающих заданий. При переполнении API отвечает `429` и `Retry-After`. Обновления одного ученика выполняются последовательно. Интерактивная работа имеет приоритет над фоновыми обновлениями. Отдельное ограничение фактических модельных запросов применяется между процессами: один локальный запрос и до четырёх внешних.

Резервирование сообщения выполняется до генерации. Зависшая после перезапуска резервация без действующей аренды через 600 секунд получает явный `unknown_outcome`. Брошенные ожидающие запросы чата освобождают очередь. Неизвестный исход начатого запроса автоматически не повторяется. Истёкшая аренда worker не позволяет старому процессу сохранить результат.

Изменение карточки или источников во время подготовки памяти делает результат задания диагностируемым отказом. Последняя готовая версия сохраняется. Исходные реплики, исправляемые наблюдения и буквальные основания известных условий помощи не удаляются.

## Проверка

`scripts/verify_memory.py` создаёт отдельную локальную БД, выполняет регрессии и контролируемую нагрузку для 5, 10 и 20 логических сессий, сохраняет отчёт и удаляет эту БД. Проверка не вызывает модель и не оплачивает публичный API. См. [инструкцию проверки](MEMORY_VERIFICATION.md) и [внешние ответы](EXTERNAL_ANSWERS.md).

Содержательная правильность учебных выводов требует преподавательского просмотра. Синтетическая нагрузка описывает компоненты приложения и имитацию задержки провайдера; она не является измерением пропускной способности публичного API.
