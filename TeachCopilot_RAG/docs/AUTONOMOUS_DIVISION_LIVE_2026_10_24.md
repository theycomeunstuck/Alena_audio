# Самостоятельное деление: проверка через браузер 24.10.2026

## Стенд и воспроизводимость

Сценарий `tests/test_autonomous_division_live_ui.py` запускает отдельные процессы
API и worker, отдельную временную PostgreSQL БД и настоящий Chromium через
Playwright. Используются рабочие `create_app`, `Store`, арифметический модуль и
`MemoryWorker`. Каждое из шести занятий начинается в новом процессе Chromium
с обычного входа ученика. Преподавательская учётная запись служит только для
подготовки привязок учеников в БД; входа преподавателя и подтверждения памяти нет.

Подменены только сервисы генерации, embeddings и RAG. Любой вызов запрещённого
сервиса сначала записывается с `fsync` в общий журнал всех перезапусков, затем
завершается ошибкой. Проверка требует отсутствия таких записей. Readiness моделей
и индекса в этом стенде относится к проверяющим адаптерам.

API и worker подключаются только к БД со случайным именем проверки на loopback.
После завершения fixture удаляет эту БД. Обычная БД приложения не изменяется.
Worker действительно получает и завершает отдельную начальную задачу без хвоста
диалога и без вызова модели; его последующие опросы очереди журналируются.

Полная команда запуска:

```powershell
.\.venv-local\Scripts\python.exe scripts/verify_local.py --ui
```

Для одного сценария нужны локальный `TEACHCOPILOT_TEST_DSN` и установленный Chromium:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = "$PWD/.local/ms-playwright"
.\.venv-local\Scripts\python.exe -m pytest -q -s tests/test_autonomous_division_live_ui.py
```

## Шесть последовательных занятий

Два синтетических ученика проходят по три занятия. Проверяются:

- Однозначный делитель по умолчанию и явный выбор двузначного.
- Неверный ответ, уточнение для «ага», «хз», «4?» и неподдерживаемого вопроса.
- Объяснение правила и отдельный показ текущего шага без продвижения.
- Вопросы и вычисления в фазах цифры частного, остатка и сноса цифры.
- Пауза, завершение занятия, закрытие браузера и продолжение без подтверждённой памяти.
- Восстановление после перезапуска API и worker.
- Следующий пример, обычное частное, внутренний и конечный ноль.
- Явная смена незавершённого примера с сохранением признака прерывания.
- Отклонение действия из второй вкладки с устаревшим состоянием.
- Отказ чужому ученику и конфликт при подмене протокола.
- Блокировка старого курсора при неизвестном исходе последнего действия.
- Архив с буквальными сообщениями и без внутренних вычислительных полей.
- `job=null`, `job_id=null` при завершении и новый автономный запрос состояния.
- Отсутствие заданий памяти и версий памяти для обоих учеников.
- Неизменность карточек и прежних сеансов обычного режима.

Ожидаемые ответы вычисляет отдельный алгоритм по десятичным цифрам, целочисленному
делению и вычитанию. Он не вызывает рабочее арифметическое ядро. Публичный курсор
сравнивается с сохранённым состоянием в PostgreSQL; текст вопроса и показа текущего
шага проверяется по этому независимому расчёту. Границы диапазона дополнительно
покрываются модульными проверками полного запуска.

## Потеря ответа после сохранения

Прокси `tests/autonomous_network_fault.py` пересылает настоящий HTTP-трафик.
Для выбранного действия он полностью получает успешный ответ рабочего API,
проверка подтверждает уже сохранённый курсор в БД, а браузеру прокси передаёт
только первый байт тела с исходной полной длиной и закрывает соединение.
Прикладные ответы прокси не создаёт.

После видимой сетевой ошибки API и worker перезапускаются. Нажатие «Повторить»
возвращает ровно тот же JSON, а SQL-проверка находит ровно одну запись действия.
Усечение тела выбрано потому, что закрытие соединения до заголовков Chromium
может незаметно повторить сам; для проверки кнопки повтора нужна видимая ошибка.

## Найденное исправление

Просмотр скриншотов выявил ошибку: после восстановления или завершения сеанса
с неизвестным исходом интерфейс мог снова показывать прежний пример и форму
ответа. `web/app.js` теперь сразу отмечает автономное состояние недоступным при
восстановлении заблокированного сеанса и после завершения обновляет автономный
контекст. Сценарий проверяет скрытие примера, вопроса и формы в обоих случаях,
а также реальный автономный GET после каждого из шести завершений.

## Целостность журналов стенда

Просмотр первого полного запуска `full01` выявил повреждённую строку общего
журнала процессов при конкурентном `O_APPEND` в Windows. Учебный сценарий в нём
прошёл, но для окончательного результата этот прогон не используется.

Helper теперь пишет отдельные UTF8 JSONL-файлы для каждого PID и роли. После
остановки дочерних процессов тест разбирает каждую строку, сопоставляет роль и PID
с именем файла и собирает общий журнал. Для успешного результата обязательны
запуски API и worker и подключения к БД каждого поколения, а также успешное
выполнение начальной задачи worker без модели. Любой файл запрещённых вызовов
приводит к отказу проверки. Две дополнительные регрессии одновременно запускают
двух писателей и проверяют полноту, порядок и Unicode для обоих видов журналов.

## Границы вывода

Это синтетическая техническая проверка. Она не оценивает освоение деления,
самостоятельность вне приложения, общую правильность свободного LLM-тьютора
или нагрузку на 20 пользователей. Неизвестный исход внесён через методы Store;
конфликт вкладок проверяет последовательное действие с устаревшим курсором.
Сценарий не воспроизводит одновременную нагрузочную гонку выбора примера.

Рабочий флаг `LOCAL_AUTONOMOUS_DIVISION_ENABLED` остаётся выключенным по умолчанию.
Слепой человеческий просмотр НИРС этим запуском не заменяется. Замороженные
материалы, документы Word/PPT и прежние журналы не изменяются.
