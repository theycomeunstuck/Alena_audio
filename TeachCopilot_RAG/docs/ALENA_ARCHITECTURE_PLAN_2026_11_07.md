## 1. Целевой результат

## 3. Поток данных

1. API авторизует аккаунт и доступ к ребёнку, определяет техническую сессию и резервирует новую реплику с идемпотентным ключом.
2. Хранилище добавляет исходный текст, роль, UTC timestamp, временные зоны и дневную принадлежность.
3. Сервер получает разрешённую собственную переписку участника, последние 20 сообщений и дневные сводки.
4. Resolver определяет намерение текущего запроса. Поле `personal_memory_recall` явно управляет обращением к полному архиву.
5. При вопросе о прошлом callback извлекает подходящие фиксированные чанки из собственного архива. Выбранные реплики возвращаются вместе с источниками, ролями, смещениями и временными метаданными.
6. Отдельно проверяется доступ к преподавательским наблюдениям через существующий reviewed grant.
7. Runtime собирает SYSTEM context, recent messages, учебные материалы и выбранные источники в пределах полного бюджета модели.
8. Ответ помощника сохраняется отдельным исходным сообщением. Производные summaries и каталог обновляются по изменению своего снимка источников.

Сбой генерации сохраняет уже принятую пользовательскую реплику и статус доставки. Повтор запроса с тем же идентификатором возвращает существующий результат либо понятный статус обработки.

## 4. Архив, время и миграция

### Исходные данные

Канонический архив строится на `memory_sources` и проверенных связях `learning_messages`. Исходные тексты имеют стабильные идентификаторы и порядок. Исправление оформляется отдельным источником со связью с исправляемой записью.

В публичной истории показываются исходные пользовательские и ассистентские тексты. Служебные поля полного model response имеют отдельный диагностический доступ.

| Поле | Смысл |
| --- | --- |
| `created_at` | Точный серверный UTC-момент регистрации исходной реплики |
| `event_timezone` | Записанная IANA-зона события регистрации. Для старых записей допустимо неизвестное значение `NULL` |
| `activity_timezone` | Зафиксированная зона, по которой сообщение отнесено к учебному дню |
| `activity_day` | Сохранённый generated day из `created_at` и `activity_timezone` |
| `learning_timezone` | Настройка календарных границ для новых записей ребёнка |
| `display_timezone` | Предпочтение пользователя для отображения timestamps |

Миграция 020 использует `Asia/Tomsk` для дневной группировки старых сообщений и сохраняет неизвестность первоначальной `event_timezone`. Новая настройка отображения действует на представление времени. Изменение учебной зоны применяется к новым источникам, исторические `activity_timezone` защищены от обычного редактирования.

Временной каталог опирается на сохранённые даты. Фразы «вчера» или «прошлым летом» описывают время рассказанного события и требуют привязки к дате исходной реплики. При отсутствии достаточных данных в ответе сохраняется неопределённость.

### Проверка миграции

- До и после применения сверить количество, идентификаторы и хеши текстов исходных сообщений.
- Применить полный набор миграций к копии предыдущей схемы, затем повторно запустить мигратор.
- Проверить UTC instants, границу полуночи, неизвестную legacy event zone и дневные границы старых записей.
- Проверить совместимость PostgreSQL с `UNIQUE NULLS NOT DISTINCT`, используемым миграцией 021.
- Проверить наличие IANA-данных в целевой Windows-среде и в PostgreSQL для `Asia/Tomsk` и пользовательских зон.

## 5. Автоматическая память и reviewed evidence

### Собственная переписка

`conversation_context` доступен после серверной проверки пары ребёнок–участник. Он собирает все темы и технические сессии этого участника. Пользовательские реплики получают смысл `self_report`, ответы помощника – `context_only`.

Для нового ребёнка собственная память подключается автоматически через обычный чат. История восстанавливается после перезапуска браузера и приложения. Сведения из рассказа ребёнка сохраняют происхождение «со слов ребёнка».

Выборка ассистентских реплик проходит через `learning_messages.assistant_source_id` и проверяет принадлежность той же переписке. Такой контракт отделяет собственный разговор ребёнка от приватных разговоров преподавателя о нём.

### Подтверждённые наблюдения

`memory_context` использует существующий reviewed grant, его source IDs, тему, recipe и проверки freshness. Подтверждение преподавателя управляет обновлением карточки, учебными выводами и доступом к преподавательским источникам.

Статус `approved` собственных детских реплик сохраняет смысл отдельного решения преподавателя. Автоматический рассказ об интересе или настроении создаёт данные для разговора и возможный черновик наблюдения. Подтверждённый устойчивый интерес и оценка освоения требуют соответствующего существующего пути проверки.

Устаревший grant исключает относящиеся к нему reviewed evidence. Собственная разрешённая переписка остаётся доступной обычному разговору.

## 6. Дневные summaries и SYSTEM context

Новый слой использует отдельную таблицу `conversation_summary_versions` из миграции 021. Его scope включает ребёнка и участника, алгоритм, снимок источников и временную политику. Summary содержит ссылки на исходные сообщения и признак происхождения каждого извлечения. Текущий контракт `build_conversation_memory` возвращает `last_day`, `last_seven_active_days`, `recent_messages` и `system_text`. Пользовательские обозначения day и last7active_days соответствуют первым двум полям.

`last_day` показывает один явно названный день. Рекомендуемая семантика карточки по умолчанию – последний активный день, с видимой датой. Это соответствует текущему построению сводок из активных дат. Поле даты обязательно, чтобы после долгого перерыва карточка правильно показывала прошлое занятие.

`last_seven_active_days` содержит до семи последних активных дат, включая последний активный день. Запрос за явно выбранный календарный день должен указывать его отдельно. Новые сообщения текущего дня обновляют его source fingerprint.

`recent_messages` содержит до двадцати отдельных сообщений. Текущий запрос включается один раз. Архивная пагинация имеет собственный размер страницы и обеспечивает доступ ко всей истории.

Рекомендуемый порядок prompt сохраняет сначала наиболее устойчивые блоки.

1. Постоянные инструкции и подтверждённый профиль.
2. Сводка семи активных дней.
3. Подробная сводка одного дня.
4. Источники полного архивного поиска и reviewed evidence текущего запроса.
5. Последние сообщения в обычных ролях.

Текст summaries входит в SYSTEM как явно ограниченный блок данных. Внутренние цитаты сохраняют статус реплик их авторов. Инструкции из процитированного разговора обрабатываются как содержание архива.

Для устойчивого префикса нужны детерминированный порядок, единое форматирование и стабильный текст при одинаковом снимке. Текущие секунды, случайные служебные идентификаторы и время повторной генерации выводятся в metadata. Изменение содержимого summary обоснованно меняет соответствующую часть префикса. Фактическое повторное использование KV-cache измеряется на целевом runtime.

Часовая точность текста summary относится к отображению. Обновление определяется изменением источников. Дополнительный LLM для построения первой extractive-версии сводок не требуется.

Полный prompt получает единый лимит вместе с system, recent messages, retrieved evidence и резервом ответа. При превышении модель получает диагностируемое сокращение целых старых блоков. API показывает доступное и включённое количество сообщений и источников. Целевой сценарий обычных коротких реплик включает все двадцать сообщений.

## 7. Полный архивный поиск

### Фиксированные чанки

Согласованный стартовый recipe задаёт окно 900 Unicode-символов и overlap 120 символов. Для исходного абзаца длиннее 1800 символов overlap увеличивается до 240. Это конкретные начальные параметры, которые затем проверяются на корпусе коротких русских диалогов и длинных рассказов.

Окна строятся детерминированно по транскрипту технической сессии. Соседние короткие реплики попадают в общий контекст. Каждая часть чанка сохраняет `source_id`, автора, роль, начальное и конечное смещение в исходном тексте. При переходе между датами чанк хранит диапазон и принадлежность входящих источников к дням.

Единица смещения – Unicode code point Python-строки. UI учитывает различие с UTF-16 offsets JavaScript при подсветке русских текстов, эмодзи и других составных символов.

Ключ чанка и embedding cache включает source IDs, текстовые хеши, chunker recipe, scope и идентичность embedding-модели. Перекрывающиеся результаты объединяются по источникам и диапазонам перед сборкой prompt.

### Retrieval

Основной кандидатный поиск использует векторы существующей BGE-M3. Лексический сигнал помогает точным именам, редким словам и явным формулировкам. Комбинация рангов должна иметь определённый и проверяемый рецепт. Влияние каждого компонента оценивается на одинаковых вопросах.

Ранее проведённый lexical-эксперимент TeachCopilot использовал PostgreSQL Russian `plainto_tsquery` и `ts_rank_cd`. Его результаты следует подписывать этим методом. Эффективность BM25 на коротких русских репликах требует отдельного измерения выбранной реализации.

Короткое «да» требует соседнего вопроса, изменение интереса требует отрицания и более поздней реплики, редкий давний факт требует доступа за пределы recent windows. Эти случаи входят в обязательный набор проверки.

Темы каталога предназначены для навигации и диагностики. Сейчас их метки не влияют на ранжирование и не ограничивают полноархивный поиск. Использование тем как сигнала поиска можно рассматривать после отдельной оценки качества классификатора и retrieval на отложенной выборке. Жёсткое ограничение дат допустимо при явно заданном и проверенном временном интервале пользователя.

Предлагаемая сигнатура владельца retrieval – `retrieve_conversation_context(store, runtime, learner_id, actor_id, query, exclude_source_id=None, budget_bytes=4000, time_filter=None)`. API передаёт серверный callback в RAG. Вызов происходит после явного решения `personal_memory_recall` существующего resolver.

## 8. Классификатор и временной каталог

### Стартовый выбор

Рекомендуемый старт использует существующие BGE-M3 embeddings и cosine similarity к фиксированным русским тематическим прототипам. Векторы прототипов вычисляются один раз на recipe. Это выбор по повторному использованию доступной модели и стоимости эксплуатации. Качество на диалогах «Алёны» проверяется отдельно. [Карточка BGE-M3](https://huggingface.co/BAAI/bge-m3).

Подготовленный кандидат отдельного предобученного zero-shot классификатора – `MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli` для CPU-проверки. Исследование карточки проведено, загрузка и локальная оценка ещё предстоят. Внедрение кандидата зависит от измерений качества, задержки и памяти. [Карточка multilingual MiniLMv2 L6](https://huggingface.co/MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli).

Cosine scores показывают степень сходства. Интерфейс подписывает их как similarity. Классификация описывает содержание разговора, включая отрицания. Фраза «не люблю шахматы» может относиться к теме увлечений, а её исходный смысл сохраняется в цитате.

Начальная общая таксономия включает учебные задания, игры и увлечения, события и рассказы, самочувствие со слов ребёнка, планы и просьбы, общение и прочее. Для чанка допустимы 0–2 темы и состояние недостаточного контекста.

Временные разделы каталога строятся из UTC timestamp, `activity_day` и сохранённых зон. Тематический классификатор обрабатывает содержание сообщения.

### Одно текущее состояние

Инвариант каталога – один активный classifier recipe с идентичностью модели, таксономией, параметрами прототипов или classifier и правилами thresholds. Текущие assignments принимаются только при точном совпадении recipe.

Для повторной обработки одного scope тем же recipe достаточно атомарной замены его производных assignments. Для смены глобального recipe требуется согласованная публикация нового current state. Остальные scopes получают явное состояние `pending` до готовности разметки нового поколения.

Порядок переклассификации следующий.

1. Зафиксировать scope, исходный watermark, хеши источников и целевой recipe.
2. Построить чанки и новые labels вне блокирующей транзакции.
3. Проверить coverage, размеры, диапазоны источников и совпадение модели.
4. Учесть источники, появившиеся во время расчёта, либо повторить обработку изменившегося scope.
5. В короткой транзакции проверить ожидаемый current state и заменить обслуживаемую разметку вместе с её recipe metadata.
6. После commit предоставить читателям новое согласованное состояние. При ошибке rollback сохраняет прежнее работающее состояние.

Текущие operational labels хранятся одним набором. Временная подготовка replacement и технический журнал операции ограничены задачей публикации. Исходный архив остаётся самостоятельным append-only источником.

Точная SQL-структура 023 ещё согласуется владельцем каталога и владельцем интеграции. Вариант с per-scope metadata обязан обеспечивать глобальный инвариант единственного активного recipe и явную маркировку устаревших scopes.

## 9. Пассивный и активный сбор

Пассивный путь записывает реальные сообщения, создаёт дневные extracts, обновляет поиск и тематический каталог. Разовые рассказы сохраняются с авторством и датой. Автоматическое извлечение интересов может предлагать преподавателю существующий review-процесс.

Активный путь начинает с одного необязательного вопроса за учебный календарный день. Формулировка короткая, соответствует возрасту и позволяет сразу перейти к заданию. При продолжающемся упражнении показ откладывается до естественной паузы.

Миграция 022 хранит check-in и события `offered`, `shown`, `skipped`, `answered`. Уникальность пары ребёнок–участник–день обеспечивает одинаковое состояние при reload, другой теме и параллельной вкладке. Показанный вопрос помощника и ответ ребёнка связаны с исходными сообщениями архива.

Ответ проходит через обычное сохранение чата. Пропуск завершает предложение на этот день. Следующий активный день допускает новый вопрос. Начальная версия использует deterministic templates и интерфейсные события внутри приложения.

## 10. Совместимость API и интерфейс

- Новые hierarchy fields подключаются в обычном server-built conversation context.
- Старые `last_session` и `last_seven_sessions` сохраняют прежний контракт существующих клиентов. Дневные карточки имеют новые имена и явно показывают дату.
- Legacy `/v1/chat/completions` получает постоянную сессию через `ensure_conversation_session` и проходит путь сохранения новых принятых реплик. Переданную клиентом прошлую историю нужно отличать от сообщений, реально принятых сервером ранее.
- Идемпотентность проверяется по стабильному идентификатору клиента. При его отсутствии сервер может гарантировать сохранность принятого запроса, а повторную доставку следует явно учитывать в контракте клиента.
- Точное время, день, display zone, source IDs и статус доставки доступны в архивных ответах API.
- Настройки display timezone и learning timezone имеют отдельные поля и проверку IANA-zone.
- UI показывает собственную автоматическую память, дату дневного summary, диапазон семи активных дней и доступ к исходным репликам.
- Для нового ученика обычный чат сразу использует доступную собственную историю. Переключение экспериментальных методов остаётся в предназначенном для этого преподавательском или исследовательском интерфейсе.
- Временные категории каталога и тематические facets ссылаются на исходную переписку. Тема разговора отображается как производная метка.
