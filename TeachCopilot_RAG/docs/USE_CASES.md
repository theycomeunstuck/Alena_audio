# Сценарии использования и примеры

Имена, наблюдения и задачи ниже относятся к синтетическим демо-профилям. Это примеры тестирования рабочего процесса, не оценки реальных детей и не клинические выводы. Темп прохождения программы гибкий; уровень класса не задаёт готовность автоматически.

## 1. Педагог выбирает ученика и смотрит карту

Педагог входит в локальный интерфейс, выбирает «ДЕМО – Луна Лис» (`demo-luna-03`) и смотрит цель, карту навыков и историю занятий. Карта различает предварительные планировочные подсказки и подтверждённые выводы по новым наблюдениям. Если подтверждающих данных нет, статус остаётся неопределённым. Смысл статусов объяснён в [политике ЗБР](ZPD_POLICY.md).

## 2. Разделить самостоятельное решение и решение с помощью

На задаче по Scratch «ДЕМО – Мика Сосна» (`demo-mika-03`) самостоятельно собирает последовательность блоков. Для другой задачи ему требуется наводящий вопрос о порядке повторений. Педагог сохраняет оба наблюдения отдельно: для каждой попытки выбирает тему, ID задачи, результат и поддержку. Разные ID или сложность означают разные задачи, они не образуют сопоставимую пару.

## 3. Проверить, уменьшается ли нужная поддержка

Для темы циклов Scratch педагог записывает самостоятельную и поддержанную попытки сопоставимой сложности под одним и тем же task_id. На следующем занятии он проводит новую пару под новым task_id. В форме наблюдения один task_id служит идентификатором пары по умолчанию. Две недавние сопоставимые пары могут подтвердить изменение уровня поддержки. Разрозненные задачи, провал только с наглядной опорой или одна удачная попытка оставляют вывод неопределённым. Статус «вне ЗБР» требует, чтобы в обеих последних парах не удались самостоятельная и совместная попытки, а успеха не было ни с одной опорой.

## 4. Сравнить задачу из источника с модельным черновиком

Педагог выбирает предмет и тему в разделе подготовки занятия. Например, для математики source-template возвращает `div-408-4`, для Scratch – `scratch-sequence-01`, для Python – `python-output-01`, если их темы выбраны и материал доступен. Педагог проверяет исходный текст, ключ и авторские подсказки. Затем выбирает «Новый черновик с локальной моделью» и просит подготовить задачи по той же теме. Второй результат требует проверки и не называется проверенным источником. Если задач с точной темой/сложностью недостаточно, source-template сообщает об этом и не подменяет материал выдуманной задачей.

## 5. Просмотреть изменение профиля и обработать конфликт

После занятия педагог вводит фактологическую заметку через «Подготовить изменение профиля». Система строит предложение, показывает изменения, предупреждения и неразрешённые данные; ничего не применяет до подтверждения. Педагог сравнивает предложение с наблюдением и подтверждает его, только если согласен. Если между просмотром и подтверждением карточка изменилась, система возвращает конфликт версии. Педагог обновляет карточку и создаёт новое предложение вместо подтверждения устаревшего.

## 6. Ученик задаёт вопрос по программированию

Ученик «ДЕМО – Ника Комета» (`demo-nika-04`) входит под собственным аккаунтом, выбирает в чате Scratch и спрашивает, почему блок с условием запускается только при выполнении условия. Помощник использует подключённый материал и может попросить ученика уточнить вопрос. Ученик видит только свой контекст и не получает заметки педагога, чужие профили или закрытый ключ ответа.

## 7. Убедиться, что чужая карточка закрыта

Ученик пытается открыть карточку другого ребёнка через API или интерфейс. Система отказывает в доступе и не включает чужие сведения в ошибку. Педагог также может просматривать только карточки, назначенные его аккаунту.

## 8. Не придумывать правило при нехватке источников

Ученик спрашивает о нестандартном Scratch-блоке, отсутствующем в курируемых материалах. Помощник должен отказаться от неподтверждённого объяснения или попросить уточнить термин. Педагог подбирает диагностическую задачу по проверенному источнику и записывает конкретный результат. Такой вопрос не изменяет mastery автоматически.

## 9. Импортировать новый материал и проверить поиск

Оператор добавляет материал в `knowledge-data/` с предметом, стабильным `topic_id`, происхождением и версией. Он выполняет импорт, затем переиндексацию по локальному руководству. После этого проверяет несколько запросов по теме и запрос вне области. Материал считается доступным только если импорт и индексация завершились, а поиск находит ожидаемый источник.

## 10. Сделать резервную копию и проверить восстановление

Оператор сохраняет базу перед обновлением материалов или схемы. Для восстановления создаёт отдельную пустую тестовую БД, загружает туда копию и проверяет вход, связи учётных записей с профилями, каталог и историю. Рабочая база не используется как цель проверки восстановления.

## Приёмочные сценарии

Проверьте вход педагога и ученика, область доступа, выбор предмета в чате, пустое состояние ЗБР, раздельные самостоятельные и поддержанные наблюдения, сопоставление пар, исходный и модельный режимы задач, конфликт ревизии предложения, отказ без источника, импорт/индексацию и восстановление в пустую базу. Полную проверку с UI можно воспроизвести по шагам в [руководстве](USER_GUIDE.md#воспроизводимая-проверка); актуальное число проверок берите из локального отчёта, а не из этого примера.
