# Руководство по интеграции памяти «Алёны» с внешним приложением

Статус: составлено 22 ноября 2026 по коду ветки `zcode/memory-docs-20261122` (база: `main` + правка quote guard, коммит `5c76022`). Документ описывает интеграционную поверхность `local_app` **в том виде, в каком она есть сейчас**, и отдельно перечисляет то, чего для интеграции не хватает. Классификация данных, на которую здесь ссылаются классы `S1`, `R1`, `D5` и т.п., – в `docs/ALENA_MEMORY_DATA_CLASSIFICATION.md`.

Контекст: на встрече команды сказано, что приложение Алексея (репетитор на основе версии Фёдора) генерирует уроки, берёт задания из банка, выдаёт ответы преподавателю, хранит «сводку предыдущего урока» (перезаписывается на каждом уроке) и «следующие шаги», полную историю не хранит; систему памяти и истории (этот репозиторий) позже предполагается «пристыковать» к его приложению. **Кода Алексея в нашем распоряжении нет**, поэтому всё, что сказано о его приложении, – со слов встречи и помечено как предположение.

## 1. Что представляет собой `local_app`

Один процесс FastAPI (`server.py` → `local_app/api.py::create_app`) плюс отдельный фоновый процесс-исполнитель (`scripts/memory_worker.py`, класс `MemoryWorker`, `local_app/memory_service.py:307`; `scripts/start_local.ps1:34` запускает и его), общая PostgreSQL с pgvector и локальная Ollama (`gemma4:12b`, `bge-m3`). Слушает по умолчанию только `127.0.0.1`. CORS-посредника в коде нет (поиск `CORSMiddleware` в `local_app/` пуст), то есть вызовы из браузера другого происхождения не предусмотрены; серверные вызовы возможны.

Что уже есть для внешнего клиента:

| Возможность | Состояние |
|---|---|
| Аккаунты, роли, сессии на токенах | есть (раздел 2) |
| Привязка ребёнка к аккаунту, доступ преподавателя | есть, но только по логину и паролю (раздел 2) |
| Запись реплик в полный архив | **только как побочный эффект чата** `POST /v1/chat/completions` (раздел 3.1) |
| Чтение истории, сводок, подтверждённой памяти, карточки | есть, с разной областью доступа (разделы 3.2-3.3) |
| Рекомендация следующего шага и её подтверждение | есть, преподавательский процесс с фоновым исполнителем (раздел 3.4) |
| Генерация уроков, банк заданий, ведомый урок | есть (пересекается с функциями приложения Алексея, раздел 4.4) |
| Быстрая память и поиск по истории как самостоятельные HTTP-методы | **нет** (раздел 3.2, пробел П2) |
| Служебная аутентификация «сервис-сервис», подмена пользователя, API-ключи | **нет** (раздел 2.4) |

## 2. Аутентификация и доступ

### 2.1. Вход и токен

`POST /auth/login` (`local_app/api.py:1311`).

Запрос (`LoginRequest`, `api.py:381`): `{"email": str 3..320, "password": str 1..1024}`. Адрес приводится к нижнему регистру и обрезается по пробелам; неизвестный и неактивный адрес стоит столько же времени, сколько верный (защита от перебора, F-074).

Ответ (`issue_login_session`, `api.py:1305-1309`):

```json
{"access_token": "<TOKEN>", "token_type": "bearer", "expires_in": 43200,
 "account": {"id": "<UUID>", "email": "...", "display_name": "...", "role": "teacher|student|admin", "learner_id": null}}
```

- Дальше во всех запросах: `Authorization: Bearer <TOKEN>` (`require_user`, `api.py:295`). Отсутствие или неверный токен – `401`.
- Срок жизни `LOCAL_SESSION_HOURS` (по умолчанию 12 часов, допустимо 1-168; `config.py:46`, проверка `config.py:78`). Хранится SHA-256 токена (`sessions.token_hash`, миграция 001). Обновления токена нет: нужен новый вход.
- `POST /auth/logout` удаляет сессию, `GET /auth/me` возвращает аккаунт, профиль (часовой пояс показа) и флаги возможностей (`api.py:1345-1368`). Проверено в демо.
- Пароль: минимум 12 символов при создании (`auth.py::hash_password`), PBKDF2-SHA256, 600 000 итераций.
- Демо-вход `POST /auth/demo/{teacher|student}` существует **только** при `LOCAL_DEMO_LOGIN=1`, только с loopback и с заголовками `Origin` и `X-TeachCopilot-Demo: 1` (`local_app/demo_login.py`). Для интеграции не используется.

### 2.2. Роли и права

| Роль | Что может | Источник |
|---|---|---|
| `student` | работает ровно с одним привязанным учеником; читает свой архив, свою иерархическую память, свой каталог, check-in; ведёт чат; видит безопасную проекцию карточки и панель | `access()` (`api.py:329`), `student_learner_id` (`api.py:339`) |
| `teacher` | работает с учениками, назначенными ему в `account_learners`; создаёт ученика, читает и меняет карточку, подтверждает память, ставит задания, ведёт уроки | `teacher()` (`api.py:310`), `access()` |
| `admin` | существует в схеме (`accounts.role`), но `access()` отвечает `403 role is not allowed` для любой роли, кроме `student` и `teacher` (`api.py:329-337`) | см. пробел П8 в классификации |

Проверено в демо: ученик на `GET /learners/{id}/memory` получает `403 teacher role required`; без токена – `401 Bearer session required`.

### 2.3. Как ученик привязывается к аккаунту

- Связь «аккаунт – ученик» – таблица `account_learners(account_id, learner_id, relationship)` (миграция 001). `relationship='student'` для ребёнка, `'teacher'` для преподавателя. Проверка доступа – `Store.authorize_learner_access` (`store.py:595`) по одной этой таблице.
- Поле `account.learner_id` в ответах входа и `/auth/me` всегда `null` (в демо проверено): ученик определяется через `account_learners`, а не через поле аккаунта (`student_learner_id` перебирает карточки и проверяет доступ, `api.py:339-348`).
- Ограничение: **один студенческий аккаунт – один ученик**. Привязка к второму ученику отклоняется (`409`, `Store.assign_learner`, `store.py:580`, защита F-033).
- Создание ученика: `POST /learners` (только преподаватель; `api.py:1530`), тело `{"learner_id": str 1..100, "card": {...}}`. `learner_id` должен совпадать с `card.learner_id`, подходить под шаблон `^[a-z0-9]+(?:-[a-z0-9]+)*$` (`store.py:15`) и быть новым (иначе `409`). Карточка проверяется `learner-data/tools/validate.py::validate_card`; обязательные поля схемы: `schema_version, learner_id, pseudonym, age_group, grade, language, rag_context, profile, interests, knowledge, error_patterns, mvp`. Темы в карточке должны существовать в каталоге (`GET /catalog`, 82 темы в демо).
- Создание студенческого аккаунта и привязка в одной транзакции: `POST /learners/{id}/students` (`api.py:1584`), тело `{"email", "display_name", "password" (>=12)}`. Привязка уже существующего: `POST /learners/{id}/student` с `{"student_email"}` (`api.py:1564`).
- Доступ преподавателя к ученику: `POST /learners` назначает созданного ученика создавшему преподавателю; назначить преподавателю **существующего** ученика HTTP-методом нельзя (сообщение `409`: «existing learners can be assigned only by an operator», `api.py:1535`).
- Создание аккаунта преподавателя: только скриптом `scripts/manage_local.py bootstrap --email --display-name --password-stdin`, который заодно назначает ему **всех** учеников, существующих на момент вызова (`manage_local.py:92-93`). HTTP-метода нет.

### 2.4. Чего нет для интеграции «сервис-сервис»

- Нет API-ключей, клиентских учётных данных, выделенной роли «сервис», подмены пользователя (act-as) и ограничения частоты запросов (поиск по `api.py`).
- Следствие для детского чата. Реплика попадает в архив ребёнка **с автором `student` только если её отправил студенческий аккаунт, привязанный к этому ученику** (`reserve_chat_message(... author_role=_role(user))`, `api.py:2169`, и `_student_session_actor`, `memory_store.py:376`: нужна роль `student`, активный аккаунт и `relationship='student'`). Если внешний сервер пересылает чужие реплики под одним преподавательским токеном, они сохранятся как реплики **преподавателя**, в отдельной области (`actor_id` аккаунта преподавателя), не будут считаться детским чатом (счётчик `memory_chat_source_revision` не растёт), а извлечение личных предпочтений откажется их использовать, потому что требует автора `student` (`unified_memory_processing.py:215-216`). Поэтому на каждого ребёнка нужен собственный студенческий аккаунт и его токен (вход по логину и паролю). Токены у внешнего сервера придётся хранить и обновлять каждые ≤12 часов.

## 3. Эндпоинты по задачам интеграции

Общие правила:

- Идентификатор ученика – строка `learner_id` в пути. Идентификаторы объектов – UUID в виде строк.
- Ошибки доступа: `401` (нет или недействителен токен), `403` (роль или чужой ученик), `404`, `409` (конфликт ревизии или повтор идентификатора с другим содержимым), `422` (валидация), `429` (очередь генерации заполнена, заголовок `Retry-After: 10`), `503` (БД, модель или подсистема недоступна). Сопоставление исключений – `memory_error` (`api.py:513`), `unified_http_error` (`local_app/unified_app.py:60`).
- Ревизии: карточка и многие записи используют **compare-and-set** по целому `revision`. Клиент обязан передавать `expected_revision` и при `409` перечитать данные.

### 3.1. Сохранение реплики и истории занятия

Единственный способ положить реплики в полный архив – чат. Отдельного метода «записать реплику без генерации» нет (пробел П2 классификации).

**Создать занятие (необязательно).** `POST /learners/{learner_id}/learning-sessions` → `201` (`api.py:890`).

- Запрос `LearningSessionRequest` (`api.py:424`): `{"topic_id": str ≤180 | null, "client_session_id": str ≤180 | null, "mode": "standard" | "autonomous_division"}`. Тема по умолчанию `general`. Повтор того же `client_session_id` для того же аккаунта возвращает ту же сессию; другая тема или режим – `409` (`create_learning_session`, `memory_store.py:504`). `mode=autonomous_division` – отдельная функция, доступна по флагам и аккаунтам; в интеграции не нужна.
- Ответ: строка сессии (`id`, `learning_session_id`, `learner_id`, `actor_id`, `topic_id`, `client_session_id`, `status`, `session_mode`, `event_timezone`, `created_at`, `completed_at`) и `topic_title`.
- Для обычного чата сессию можно не создавать: сервер сам открывает (или переиспользует) активную сессию «стандартного» режима для пары «аккаунт – тема цели из карточки или `general`» (`ensure_conversation_session`, `memory_store.py:527`, вызов `api.py:2105-2118`).

**Реплика ребёнка и ответ.** `POST /v1/chat/completions` (`api.py:2044`). Подробная таблица поведения – в разделе 3.5. Минимальный вызов от студенческого аккаунта:

```bash
curl -s -X POST http://127.0.0.1:8099/v1/chat/completions \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"<ТЕКСТ РЕПЛИКИ>"}],
       "learning_session_id":"<SESSION_ID>","client_message_id":"msg-0001"}'
```

Если `learning_session_id` задан, `client_message_id` (1-180 символов) обязателен (`api.py:2130-2131`). Повтор с тем же `client_message_id` и тем же текстом возвращает сохранённый ответ (`api.py:2176-2196`); с другим текстом – `409`; пока предыдущее сообщение той же сессии обрабатывается – `409 message is already processing`.

**Завершить занятие.** `POST /learning-sessions/{learning_session_id}/complete` → `202` (`api.py:934`). Доступ: владелец сессии. Закрывает сессию, ставит фоновые задания `memory_update` (подтверждаемая память и кандидаты интересов) и `session_process` (сводка занятия, извлечение предпочтений и кандидатов), если не включён автономный режим. Ответ: строка сессии плюс `job`/`job_id`, `session_summary_status`, `session_processing_status` (`queued` или `enqueue_failed`). Нельзя завершить сессию с сообщением в обработке (ошибка `ValueError` превращается в `422`, `complete_learning_session`, `memory_store.py:919`).

**Прочитать историю.**

| Метод и путь | Кому | Ответ (ключи, проверено в демо) |
|---|---|---|
| `GET /learners/{id}/conversation-history?before_source_order=&limit=1..100` (`api.py:1393`) | автор (ученик видит свой, преподаватель – **свой** разговор, не ребёнка) | `{learner_id, messages:[{source_id, source_order, author_role, role, text, content, created_at, learning_session_id, topic_id, event_timezone, activity_timezone, activity_day, usage, delivery_status, pair_source_id, paired_source_id, actor_role, original_source_role, learner_id, actor_id, superseded_by}], next_before_source_order}` |
| `GET /learners/{id}/learning-sessions/current` (`api.py:848`) | автор | `{available, learning_session_id, topic_id, session_mode, status, messages:[{role, content, delivery_status, created_at, event_timezone, activity_timezone, activity_day}], history_truncated, unresolved_status, subject_id, topic_title}` |
| `GET /learners/{id}/learning-sessions?before=` (`api.py:860`) | автор | `{sessions:[{learning_session_id, topic_id, session_mode, completed_at, created_at, event_timezone, subject_id, topic_title}], next_cursor}` – только завершённые |
| `GET /learners/{id}/learning-sessions/{sid}/history?before=` (`api.py:874`) | автор, только завершённые (`409` иначе) | `{learning_session_id, topic_id, session_mode, status, messages, next_cursor}`, до 20 сообщений на страницу |

Важно: чтение «чужой» истории по сессии запрещено – `PermissionError` для не-автора (`memory_store.py:650-651`). Преподаватель не может прочитать архив чата ребёнка постранично; он видит реплики завершённых занятий через `GET /memory` (источники) и сводки (раздел 3.2).

**Заметка преподавателя (в архив как одобренная реплика).** Двухшаговый процесс: `POST /learner/update` (`api.py:1894`) принимает `{"notes", "learner_ids", "apply": false, "mode"?, "confirmed_topics"?}`, модель строит черновик карточки и возвращает `proposal_id`; затем `POST /lessons/proposals/{proposal_id}/confirm` (`api.py:1968`) применяет карточку и записывает заметку как одобренную реплику `teacher` (`_confirm_memory_proposal`, `memory_store.py:1673`). Исправление существующей реплики: `POST /learners/{id}/memory/sources/{source_id}/corrections` (`api.py:627`), тело `{"text" ≤2000, "expected_revision", "expected_source_revision", "client_correction_id"}` → `202`.

### 3.2. Контекст памяти ученика (припоминание, сводки, подтверждённая память)

Готовых «одним вызовом» методов для внешнего приложения нет. Что доступно:

**Чего нет** (проверено по списку маршрутов и по `openapi.json` демо):

- метода «быстрая память ученика» (интересы, избегаемое, цель, ошибки, незавершённый урок) – эта функция есть только как `UnifiedMemoryService.fast_memory` (`unified_memory.py:198`), которую вызывают чат и генерация урока;
- метода «найди в истории ученика по запросу» – `UnifiedMemoryService.recall` (`unified_memory.py:313`) вызывается только изнутри чата после решения resolver;
- метода получения сводки «предыдущего урока» для внешней генерации – `previous_lesson_context` (`unified_memory.py:284`) вызывается только worker-ом.

Для внешнего приложения это означает: прочитать быструю память без чата можно только косвенно – карточкой (S1) и списком принятых изменений (S5, `memory-changes`, только преподаватель, с полями `status`, `scope`, `value`).

### 3.3. Карточка ученика (источник истины – PostgreSQL, F-071)

После решения F-071 (22 ноября 2026) `teachcopilot.learners` – источник истины; JSON-файлы `learner-data/learners/*.json` – лишь начальное наполнение и цель экспорта (`scripts/export_learner_cards.py`, `tests/test_card_store_canonical.py`). Внешнее приложение **не должно** считать JSON-файлы актуальными и не должно писать в них.

| Операция | Метод | Права | Запрос | Ответ и правила |
|---|---|---|---|---|
| Прочитать | `GET /learners/{id}` (`api.py:1613`), `GET /profile?learner_id=` (`api.py:1602`) | преподаватель: вся карточка; ученик: `_safe_student_card` | – | `{learner_id, profile:{...карточка...}}`. Ревизии в этом ответе **нет**; её отдают `GET /learners/{id}/dashboard` (поле `revision`, в ответе преподавателя) и список `GET /learners` (`revision`, `updated_at`, для преподавателя) |
| Список | `GET /learners` (`api.py:1516`) | любая роль | – | преподаватель: `{learners:[{learner_id, pseudonym, grade, age_group, language, revision, updated_at}]}`; ученик: один элемент с безопасной проекцией |
| Заменить целиком | `PUT /learners/{id}` (`api.py:1547`) | преподаватель | `{"expected_revision": int ≥1, "card": {...}}` | валидация `validate_card`; `{learner_id, revision, updated:true}`; `409` при чужой правке; сохраняется снимок в `card_audit` (`store.py:249`) |
| Создать | `POST /learners` (`api.py:1530`) | преподаватель | `{"learner_id", "card"}` | `201 {learner_id, revision, created:true}` |
| Записать наблюдение по задаче (меняет числа) | `POST /learners/{id}/observations` (`api.py:1728`) | преподаватель | `ObservationRequest` (`api.py:454`): `{expected_revision, topic_id (из каталога), task_id, solved: bool (строго), support_level: "independent"\|"hint_question"\|"visual"\|"joint", assessment_pair_id?, difficulty?: "easy"\|"medium"\|"hard", notes? ≤1000, observed_on?: date}` | код `learner-data/tools/zpd.py::record_observation` пересчитывает EMA (`alpha=0.4`), зону и статус знания и сохраняет карточку; ответ `{learner_id, revision, observation{...}, zpd{...}}`. | Каталог тем | `GET /catalog` (`api.py:1498`) | любая роль | – | `{topics:[{topic_id, title, subject_id, grade, prerequisites[]}]}` |

curl -s -X POST http://127.0.0.1:8099/learners/<LEARNER_ID>/observations \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \

- Прямой записи числа `mastery` или зоны через HTTP нет и не должно быть: это нарушило бы принцип «модель и внешняя система не задают числа».
- Любое сохранение карточки увеличивает `learners.revision` и делает идущие фоновые задания `next_step` устаревшими (`finish_memory_job`, `memory_store.py:1326-1360`, ошибка `stale_revision`).
- Перечисленные в карточке `interests` – основной «быстрый» признак для планирования урока. Но эффективное значение интересов, учитывающее разговор, – это карточка плюс журнал `unified_personal_changes` (`fast_memory`); HTTP-метода «эффективные интересы» нет (см. 3.2).

### 3.4. Следующий шаг и его подтверждение

Процесс преподавателя в три шага; ему нужен запущенный `scripts/memory_worker.py` и локальная модель.

1. **Запросить.** `POST /learners/{learner_id}/next-step` → `202` (`api.py:569`), только преподаватель. Запрос `NextStepRequest` (`api.py:419`): `{"topic_id": str 1..180, "method": "profile_only"|"tail"|"summary"|"structured"|"structured_v2"|"personal_graph"|"personal_memory" (по умолчанию "tail"), "expected_revision": int ≥1 | null}`. Метод по умолчанию на стороне сервера – `personal_memory` (поле `default_method` в ответе `GET /memory`, когда память включена); `personal_graph` требует флага и Neo4j (`503` иначе). Ответ: `{"job_id", "status", "learner_id"}`. Идемпотентного ключа у этого запроса нет: каждое обращение создаёт новое задание. Очередь вмещает до 40 ожидающих запросов (`429` дальше).
2. **Дождаться результата.** `GET /memory/jobs/{job_id}` (`api.py:584`). Статусы `queued → running → completed | failed | unknown_outcome`. Преподавателю отдаётся вся строка задания, в `result` лежат действие и `next_step_id`, `memory_version_id`, предупреждения и `calls`. Опроса через вебхук нет – только периодический `GET`.
3. **Подтвердить версию памяти.** `POST /learners/{learner_id}/memory/versions/{version_id}/confirm` (`api.py:642`), тело `MemoryConfirmRequest` (`api.py:429`): `{expected_revision: int ≥1, acknowledge_new_messages: bool, expected_source_revision?: int, interest_candidate_ids?: [str ≤16], reviewed_full_archive: bool, allow_full_archive: bool, archive_snapshot_fingerprint?: sha256-hex}`. Ответ `{learner_id, version, confirmed:true, refresh_required}`. Подтверждение привязано к отпечаткам: смена кода, модели, архива или карточки делает его устаревшим (ADR-002).
4. **Использовать рекомендацию.** `POST /task/design` (`api.py:1830`) с `{"learner_id", "topic_id"?, "count"?, "mode":"generated"|"source_template", "next_step_id"?}` строит черновик заданий; при `next_step_id` проверяет, что ревизии карточки и источников не изменились (`409` иначе). Ответ: `{card, mode, review_required:true, status:"draft", next_step_id, hints_origin, text_for_child, text_for_tutor}`.

Оговорки: отдельной операции «одобрить рекомендацию» нет – одобряется версия памяти, а сама рекомендация остаётся черновиком (`review_required`). Рекомендация строится из проекции карточки (`profile_projection`: класс, язык, интересы, «избегать», цель) и текста памяти, не из журнала занятий.

Параллельный процесс с тем же шаблоном – **генерация урока**: `POST /learners/{id}/lessons` → `202` с `{"topic_id", "minutes": 5..90, "client_request_id"}` (идемпотентность по `client_request_id`), результат читается `GET /learners/{id}/lessons[/{lesson_id}]` и подтверждается `POST .../lessons/{lid}/confirm` (`api.py:1045-1100`).

### 3.5. Путь `/v1/chat/completions` и `/v1/models`

`GET /v1/models` (`api.py:2040`) требует Bearer-токен и отдаёт одну модель `teachcopilot-rag` (проверено в демо). `POST /v1/chat/completions` (`api.py:2044`) – не прозрачный прокси к модели, а **весь серверный диалоговый конвейер Алёны** с OpenAI-подобной оболочкой.

| Вопрос | Ответ по коду |
|---|---|
| Требует ли личность ученика? | Да. Для `student` ученик определяется аккаунтом. Для `teacher` нужно `learner_id` в теле или в `metadata.learner_id` (`api.py:2056-2059`); иначе `422`. Доступ проверяется. Карточка должна существовать (`404`) |
| Сохраняет ли сообщения? | Да, всегда при наличии хранилища: если `learning_session_id` не указан, создаётся или переиспользуется автоматическая сессия, а `client_message_id` генерируется на сервере (`api.py:2105-2118`). Сохраняются **только последняя реплика `user` из запроса и ответ ассистента**; прочие сообщения запроса не записываются и, при включённой памяти, **заменяются** историей сессии из базы (`api.py:2225-2227`). Поэтому клиенту достаточно присылать одну реплику |
| Какие поля запроса использует? | `messages` (только роли `user` и `assistant`, до 200 штук, каждая 1-12000 символов; роль `system` и прочие **отбрасываются**), `learner_id` (только преподаватель), `learning_session_id`, `client_message_id`, `metadata.learning_session_id`, `metadata.client_message_id`, `metadata.learner_id`, `metadata.memory_method` (`personal_memory` или экспериментальный `personal_graph`), `metadata.subject_id`, `metadata.checkin_id`, `metadata.lesson_mode="guided"`, `metadata.quality_row_id` (корреляция для оценки), `learning_action`, `learning_protocol` (явные учебные действия, автономное деление; в интеграции не нужны) |
| Какие поля игнорирует? | `model` (всегда локальная модель), `stream` (ответ всегда обычный JSON, не `text/event-stream`; в `api.py` слова `stream` нет), `temperature`, `tools` и прочие параметры выборки (комментарий `api.py:2081-2082`) |
| Что подмешивается к ответу? | Resolver (вызов локальной модели) решает: учебный вопрос, разговор, творческое продолжение, припоминание прошлого, уточнение. Далее: профиль-проекция (`prompt_text`), быстрая память `fast_memory`, предпочтения, собственный разговор (20 реплик, день, 7 дней), подтверждённая память (`tail` по умолчанию, либо `personal_memory` по метаданным), найденные учебные источники из банка заданий; при припоминании – поиск по архиву (чанки, FTS + вектор, RRF) и защита дословных цитат. Подробно – классификация, раздел 5.2 |
| Что отдаёт? | `{id, object:"chat.completion", created, model, choices:[{index, message:{role:"assistant", content}, finish_reason}], citations, sources, usage:{prompt_tokens, completion_tokens, total_tokens}, answer_routing, [retrieval_context], [query_resolution], [conversation_context]}` плюс `learning_session_id`, `client_message_id`, `memory_version_id`, `memory_stale`, `memory_method`, `checkin_id` (`rag.py:853-880`, `api.py:2510-2516`). Ученику поля `legal_name, journal, points_ledger, answers, solution` вырезаются, а `sources`/`citations` сводятся к `id, source_file, score, similarity` (`_safe_student_completion`, `api.py:183`) |
| Идемпотентность | по `(learning_session_id, client_message_id)` и SHA-256 текста (`learning_messages`, миграция 010) |
| Задержка и ёмкость | Один запрос = как минимум вызов resolver и вызов генерации локальной модели; возможны эмбеддинги. Ожидание допуска до `min(180 с, LOCAL_REQUEST_TIMEOUT)`, затем `429`; не более 40 одновременно ожидающих (`CHAT_ADMISSION_WAITER_CAP`, `api.py:60`), дальше `503`. Одновременная локальная генерация – одна (`generation_admission`, миграция 011). Измерений времени ответа не проводилось |
| Что с ошибками модели? | Принятая реплика ребёнка остаётся в архиве со статусом доставки (`failed` или `unknown_outcome`). Автоматического повтора нет: повтор с тем же `client_message_id` даёт `409 previous message outcome is unavailable; automatic retry is disabled` (`api.py:2197-2199`), нужно отправить новый `client_message_id` |

Пример для преподавательского аккаунта (отладка, ответы от имени преподавателя; **не** для детского чата, см. 2.4):

```bash
curl -s -X POST http://127.0.0.1:8099/v1/chat/completions \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -d '{"learner_id":"<LEARNER_ID>","messages":[{"role":"user","content":"Что мы разбирали вчера?"}]}'
```

## 4. Варианты интеграции

### 4.1. Допущения о приложении Алексея (предположения со встречи)

Генерация уроков, задания из банка, ответы преподавателю, сводка предыдущего урока (перезаписывается), следующие шаги, нет полной истории. Язык и стек неизвестны, способ хранения данных неизвестен, как идентифицируются пользователи и откуда берётся ребёнок – неизвестно, использует ли он облачную модель – неизвестно.

Сопоставление с `local_app` (по описанию встречи, **не проверено** на его коде):

| Приложение Алексея | Ближайший аналог в `local_app` | Различие |
|---|---|---|
| Генерация урока | `POST /learners/{id}/lessons` → `lesson_generate` (S8) | у нас черновик, кодовая проверка формата, подтверждение преподавателя, ответы вырезаются для ученика |
| Задания из банка | `materials` + `POST /rag/search`, `POST /task/design`, каталог задач урока (S10, S8) | банк 147 заданий (14 файлов), темы 3-4 класса по математике и Python/Scratch |
| Ответы преподавателя | `answers_text`, `answer_sections`, `audience=teacher` | – |
| Сводка предыдущего урока (перезаписывается) | `unified_summary_versions` (D5), `previous_lesson_context` | у нас версии неизменяемы, предыдущие остаются |
| Следующие шаги | `next_steps` (D8), «Следующий шаг» в D5 | – |
| Нет полной истории | полный архив `memory_sources` (R1) | именно это он получает от памяти |

### 4.2. Вариант 1: приложение Алексея вызывает API `local_app` как сервис памяти

Клиент-серверная схема: приложение Алексея ведёт уроки, а в `local_app` хранит историю, берёт из него сводки, карточку и профиль.

- Плюсы: используется уже написанный и проверенный контракт доступа (роли, ревизии, идемпотентность); инварианты базы (триггеры, проверки) не обходятся; обновления схемы не ломают клиента, пока API стабилен (фасад `UnifiedMemoryService` в докстринге: «Client B depends on this facade, not on its table layout»); данные ребёнка остаются на одной машине; изоляция процессов; независимый язык клиента.
- Минусы: сегодня API для этой роли неполон (нет записи реплики без генерации, нет «быстрой памяти» и припоминания, нет «сервисного» токена); нужна доработка `local_app`; вызовы по HTTP; токены ребёнка живут ≤12 часов; единственное окно локальной генерации (память и чат делят ресурс).
- Нужные доработки: раздел 5.

### 4.3. Вариант 2: общая схема PostgreSQL или подключение библиотеки

Две подварианта: (а) приложение Алексея пишет и читает таблицы `teachcopilot.*` напрямую; (б) оно импортирует `local_app` как Python-библиотеку (`UnifiedMemoryService(store, runtime)`, `Store(dsn)`).

- Плюсы: нет сетевого слоя, минимальная задержка; (б) даёт доступ к `fast_memory` и `recall` без новых маршрутов.
- Минусы: (а) обходит защиту: правила доступа и области (`actor_id`, роль автора) соблюдаются в Python-коде, не в базе; триггеры запрещают менять текст и время реплик, `CHECK`-ограничения требуют корректных статусов; `learners.card` должна пройти внешний валидатор `validate_card`; записи требуют счётчиков ревизий (`memory_source_revision`, `memory_chat_source_revision`, `unified_changes_revision`) – пропуск ломает fail-closed проверки подтверждённой памяти (ADR-002); таблицы – внутреннее устройство, миграции аддитивны, но сопровождаются одной командой; (б) требует того же интерпретатора и версий Python 3.12, `psycopg2`, `pgvector`, доступа к Ollama, и связывает релизы двух проектов; ни одна из этих схем не задокументирована как поддерживаемая внешним контрактом, кроме фасада.
- Оценка: **не рекомендуется** как основной путь. Допустим узкий вариант (б) только для чтения в одном процессе, если стек Алексея – Python и команды согласуют релизы (**не проверено**, что стек Python).

### 4.4. Вариант 3: приложение Алексея использует `/v1` Алёны как свой эндпоинт модели

Приложение Алексея вместо вызова модели обращается к `POST /v1/chat/completions`.

- Плюсы: ноль доработок на стороне `local_app` для открытого диалога; вся память, припоминание, защита цитат и конфиденциальности подключаются автоматически; OpenAI-подобная форма запроса.
- Минусы: это **не** замена модели, а замена всего диалогового слоя: `system`-сообщения клиента отбрасываются, `model`, `stream`, `tools`, температура игнорируются, история клиента заменяется серверной, ответ формируется с учётом собственной логики Алёны (resolver, ограничение учебной областью). Уроки, задания из банка и логику «следующих шагов» приложения Алексея такой путь не заменяет и не использует; поток не поддерживается; нужен студенческий аккаунт на каждого ребёнка и его токен (2.4); на каждый ход – минимум два вызова локальной модели; приложение Алексея не получит структурированные данные (только текст ответа и `sources`).
- Оценка: подходит как **экспериментальный быстрый путь для открытого диалога** (чат «спроси помощника»), но не как интеграция памяти в уроки.

### 4.5. Рекомендация

**Вариант 1 (внешнее приложение как клиент API `local_app`), в три этапа**, с `local_app` как хранилищем истории и источником истины карточки.

Обоснование:

1. Только этот вариант сохраняет инварианты, на которых построена память: неизменяемость реплик, автор-роль, области по аккаунту, ревизии и подтверждения преподавателем. Варианты 2(а) и 2(б) переносят их соблюдение на команду Алексея.
2. Он отделяет «что помнить» (память Алёны) от «как вести урок» (приложение Алексея), что и просили на встрече («пристыковать»).
3. Он совместим с обоими возможными стеками (любой язык).
4. Вариант 3 можно добавить позднее для открытого диалога без изменения архитектуры.

Этапы:

- **Этап 0 – без изменения кода `local_app`.** Приложение Алексея читает карточку и профиль (`GET /learners/{id}`, `GET /catalog`), панель и зоны (`GET /dashboard`) преподавательским аккаунтом; передаёт результаты уроков как наблюдения (`POST /observations`); для открытого диалога использует студенческие аккаунты и `/v1/chat/completions`. История уроков Алексея в этом этапе в архив не попадает.
- **Этап 1 – минимальные доработки `local_app`** (список в 5): запись реплик без генерации; чтение быстрой памяти и припоминания; сервисная аутентификация.
- **Этап 2 – двусторонний обмен**: сводки уроков из приложения Алексея записываются как версии D5; следующие шаги и сводки читаются обратно; сопоставление пользователей и тем; события вместо опроса.

## 6. Что спросить у Алексея

1. Стек и среда: язык, фреймворк, где запускается (та же машина, что `local_app`, или другая), есть ли доступ к PostgreSQL и Ollama, версии Python.
2. Идентификаторы: откуда берётся пользователь (регистрация, школа, внешний провайдер), формат идентификатора ребёнка, есть ли у ребёнка собственный логин; можно ли завести по одному студенческому аккаунту `local_app` на ребёнка.
3. Модели: какая модель генерирует уроки и ответы (локальная или облачная); можно ли передавать данные ребёнка во внешний сервис; кто отвечает за согласие родителей.
4. Данные приложения: схема «сводка предыдущего урока» (поля, длина, формат), «следующие шаги», результаты заданий (что известно: решил ли, сколько подсказок, время), формат ответов преподавателю, формат банка заданий и его соотношение с нашими 147 заданиями и 82 темами.
5. Темы и цели: используются ли идентификаторы тем, совместимые с `catalog/math_g3_g4.json` и `programming.json`; нужно ли расширять каталог.
6. Что именно он хочет получать от памяти: интересы, зоны, ошибки, незавершённый шаг, сводку, припоминание по запросу; в какой момент (до урока, во время, после); допустима ли задержка в секундах или минутах.
7. Что он готов записывать: реплики урока, события, результаты задач; доступна ли исходная метка времени каждой реплики; есть ли исторические данные для импорта.
8. Кто принимает решения: подтверждает ли преподаватель в его приложении (память, рекомендации, кандидаты наблюдений) или нужен интерфейс `local_app` (веб-интерфейс преподавателя уже есть).
9. Нагрузка: число детей, одновременных сессий, ожидаемая задержка ответа; допустимо ли одно окно локальной генерации.
10. Сроки и владельцы: кто и когда готов принять доработки API (раздел 5), кто сопровождает совместную среду, как согласуются версии и миграции.
11. Нужен ли ему вариант 3 (чат Алёны как готовый компонент) для открытого диалога, или только данные.
12. Требования к хранению, удалению и экспорту данных ребёнка с его стороны.

## 7. Приложение: сводка проверок и памятка

### 7.1. Что проверено в демо (только чтение, один пользователь на каждую роль)

`POST /auth/demo/teacher` и `/auth/demo/student`; `GET /auth/me` (обе роли); `GET /learners`; `GET /learners/demo-nika-04` (преподаватель и ученик); `/dashboard`; `/memory` (преподаватель; ученик получил `403`); `/memory-changes`; `/lessons`; `/lesson-assignments`; `/conversation-memory`; `/conversation-history`; `/conversation-catalog`; `/learning-sessions/current`, `/learning-sessions`; `/learning-sessions/{sid}/processing-result` (обе роли); `/learning-sessions/{sid}/lesson-state`; `/memory/diagnostics/index`; `/catalog`; `/v1/models`; `/openapi.json`; запрос без токена (`401`). Побочный эффект: `GET /learners/demo-nika-04/checkin` для ученика – это «получить или создать»: он создаёт запись check-in на текущий день в демо-базе (`checkins.py::get_or_create_checkin`); других записей не создавалось.

### 7.2. Что не проверялось

Вызов `POST /v1/chat/completions`, `POST .../next-step`, `POST .../observations`, создание сессий, вход по паролю (`/auth/login`), любые записи; поведение при нескольких параллельных клиентах; фоновый worker; сетевые настройки вне loopback. Всё это описано по коду.

### 7.3. Минимальная последовательность для проверки на стенде

```bash
# 1. вход (учебный аккаунт, не демо)
curl -s -X POST http://127.0.0.1:8099/auth/login -H "Content-Type: application/json" \
  -d '{"email":"<EMAIL>","password":"<PASSWORD>"}'
# 2. проверка роли и возможностей
curl -s http://127.0.0.1:8099/auth/me -H "Authorization: Bearer <TOKEN>"
# 3. карточка и каталог (преподаватель)
curl -s http://127.0.0.1:8099/learners/<LEARNER_ID> -H "Authorization: Bearer <TOKEN>"
curl -s http://127.0.0.1:8099/catalog -H "Authorization: Bearer <TOKEN>"
# 4. сводка занятия (автор или преподаватель)
curl -s http://127.0.0.1:8099/learners/<LEARNER_ID>/learning-sessions/<SESSION_ID>/processing-result \
  -H "Authorization: Bearer <TOKEN>"
# 5. рекомендация (преподаватель; нужен memory_worker)
curl -s -X POST http://127.0.0.1:8099/learners/<LEARNER_ID>/next-step \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -d '{"topic_id":"<TOPIC_ID>","method":"personal_memory"}'
curl -s http://127.0.0.1:8099/memory/jobs/<JOB_ID> -H "Authorization: Bearer <TOKEN>"
```

### 7.4. Таблица кодов состояния

| Код | Типичные причины |
|---|---|
| 401 | нет, неверный или просроченный токен |
| 403 | чужой ученик, роль не подходит, сессия принадлежит другому аккаунту |
| 404 | ученик, сессия, задание, урок не найдены; функция выключена флагом |
| 409 | конфликт ревизии; повтор идентификатора с другим содержимым; сообщение ещё обрабатывается; ученик уже привязан; память требует подтверждения или обновления |
| 413 | память и последняя реплика не помещаются в контекст модели |
| 422 | ошибка валидации (тело, длина, тема, дата) |
| 429 | очередь генерации или памяти заполнена (`Retry-After: 10`), истёк срок ожидания допуска |
| 502 | модель или чат вернули ошибку |
| 503 | БД или модель недоступны; подсистема выключена; фасад единой памяти недоступен |
