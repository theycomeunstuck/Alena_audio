# ADR-003: Context floor and UTF-8 byte budgets for approved memory

- Status: Accepted (2026-11-14)
- Implementation: truncation guard and budgets predate the date; the 8k failure was proven and the 16k floor documented on 2026-11-14 (commits `a2825bd`/`ffe19d8`)
- Key files: `local_app/personal_memory_contract.py`, `local_app/personal_graph_contract.py`, `local_app/runtime.py`, `local_app/rag.py`, `research_memory/personal_memory_lab/runtime.py`

## Context

The product rule is that approved memory may never be silently cut: a teacher approves whole source turns together with their correction links, and cutting lines can detach a correction from its source or remove an unknown-assistance condition, so an invalid context fails explicitly (`local_app/rag.py:970-988`, docstring at `973-976`). At the same time the local Ollama server has historically been able to silently truncate an oversized prompt and report the truncated token count as if it were complete (`research_memory/personal_memory_lab/runtime.py:77-79`).

The deployment discovered on 2026-11-13/14 that the half-context truncation behavior interacts with model availability: Ollama 0.24.0 could not even load `gemma4:12b`; after upgrading to 0.40.16 the server rejects oversized inputs instead of truncating them, and the two rejection wordings (Ollama ≤0.3x and ≥0.40) are both recognized explicitly (`research_memory/personal_memory_lab/runtime.py:42-49`, `_context_overflow` at `30-51`).

## Decision

1. **Tiered UTF-8 byte budgets.** Selection and whole-memory limits are derived from the model context: `personal_memory_budgets` refuses anything below 8192 and returns (3000, 4000) at 8k, (10000, 12000) at 16k, (20000, 24000) at 32k (`local_app/personal_memory_contract.py:10-18`); the graph contract fixes (10000, 12000) / (20000, 24000) for 16k/32k (`local_app/personal_graph_contract.py:57-68`). Budgets are UTF-8 byte upper bounds, not token counts (`local_app/personal_memory_contract.py:11`; the application counter is explicitly a "conservative application-only upper bound, not an exact Gemma count" at `local_app/personal_graph_memory.py:790-792`).

2. **The memory payload is validated against the budget before it can reach a prompt.** Selection fits exact canonical payload costs and a final hard check refuses overflow (`select_context`, `local_app/personal_memory.py:263-304` and `local_app/personal_graph_memory.py:674-676`); session summaries are appended only while the whole-memory budget holds (`local_app/memory_service.py:251-258`); the prompt wrapper re-checks the approved text with the same limit as generation and query resolution (`approved_memory_fits_budget`, `local_app/personal_graph_contract.py:71-91`; enforced at `local_app/rag.py:986-987`).

3. **The complete-memory path refuses truncation instead of allowing it.** Inside the approved-memory request scope, `OllamaRuntime.chat` skips history bounding, pre-checks the whole input against `(context_tokens – max_output_tokens) × 2` UTF-8 bytes and raises rather than cut (`local_app/runtime.py:415-429`), and sends `truncate=False, shift=False` to Ollama (`local_app/runtime.py:442-445`); embeddings get `truncate=False` in the same scope (`local_app/runtime.py:377-378`). Conversation prompt bounding uses the same ×2 estimate and only ever drops whole messages, never cuts text (`local_app/runtime.py:89-119`). Output-side truncation is detected via `done_reason` and rejected (`local_app/runtime.py:474-476`), and graph-memory writer calls additionally require Ollama's explicit completion confirmation (`local_app/memory_service.py:322-325`); writer inputs pass a budget diagnostic with a saturation guard (`local_app/memory_service.py:281-282`, `326-327`).

4. **Strict overflow guard on the model transport.** The lab transport forces `truncate=False` on chat/generate and `/api/embed`, preflights prompts near the boundary with a measured token count, and converts the server's overflow rejection into `ContextWindowOverflow` (`research_memory/personal_memory_lab/runtime.py:71-120`, probe refusal at `163-173`). `verify_no_truncation` sends oversized probes to generate, chat and embed and **fails closed** if the server does not reject them (`research_memory/personal_memory_lab/runtime.py:122-139`); the experimental graph provider wires this probe into model construction (`local_app/personal_graph_memory.py:916-919`).

5. **The 16k context floor is a hard de-facto requirement for the full memory chat cycle.** The graph method refuses any context other than 16384/32768 at startup (`local_app/personal_graph_memory.py:756-757`; config-level gate at `local_app/config.py:74-78`; lab `LocalModel` at `research_memory/personal_memory_lab/runtime.py:62-63`). For `personal_memory` the code nominally allows 8k – `SourceModel` accepts it and budgets shrink to 3000/4000 bytes (`local_app/personal_memory_contract.py:18`). What actually happens at 8192: the complete-memory input (conversation summary + approved memory + materials + history) exceeds the ×2 byte cap, the runtime raises, and a real chat returns HTTP 413 (`local_app/api.py:1996-1999`) or 502 through other routes (`local_app/api.py:2004-2005`) – verified independently twice on 2026-11-14 (`docs/ALENA_MEMORY_DEVOPS_MANUAL_2026_11_14.md`, section 4b). The graph channel also cannot activate at 8k, because indexes are only buildable at 16k/32k and the config fingerprint binds the context an index was built with (`local_app/personal_graph_index.py:83-84`), so the channel degrades with `no_ready_index` (ADR-001). Production therefore runs `LOCAL_CONTEXT_TOKENS=32768`, and the current deployment sets it in `.local.env`.

6. **Why byte budgets make the unified path safe even under lenient truncation.** The approved payload is small (12000/24000 bytes at 16k/32k), byte-exact-validated before prompt assembly, and re-checked at prompt build; the application-level pre-check at `local_app/runtime.py:428` makes an oversized whole input an explicit error, not a silent cut. Even a hypothetical server that ignored `truncate=False` would hit the app-side checks first; any residual truncation boundary would land on untrusted retrieved materials or history – never silently inside approved evidence, because approved evidence is never the part that overflows. Byte counting is deterministic across platforms and independent of tokenizer drift, which a token estimate is not.

## Alternatives considered

- **Token-accurate budgeting with the model tokenizer.** Rejected for the application path: it would require a tokenizer dependency and per-call tokenization; the ×2 UTF-8 heuristic plus the server-side hard rejection plus byte-exact payload validation achieve the same guarantee (nothing approved is silently lost) with simpler, auditable arithmetic. The lab runtime keeps a measured `count()` for research probes (`research_memory/personal_memory_lab/runtime.py:153-174`) with its own near-boundary refusal (`UnsafeMemoryProbe`).
- **Allow 8k with degraded memory (the (3000, 4000) tier) as a supported mode.** Not viable in practice: the full chat cycle fails at 8192 with 413/502 regardless of how small the memory payload is, because the conversation summary and latest message alone must fit uncropped. The tier remains in code but is documented as unsupported for the personal-memory chat path (open question below).
- **Trust Ollama's `truncate` flag alone.** Rejected: the discovery was precisely that an older server silently truncated while reporting a complete result; the guard therefore layers app-side byte checks, `truncate=False`, the server's 0.40+ rejection, and `verify_no_truncation` as a fail-closed probe of the actual server behavior.

## Consequences

- Approved evidence is either served whole or the request fails with a diagnosable status (413/502/409); silent half-context loss is structurally excluded on the application path.
- Context sizing becomes an operational requirement, not a tuning knob: lowering `LOCAL_CONTEXT_TOKENS` below 16384 breaks the personal-memory chat path at runtime even though the server starts, and (per ADR-002) changing it stales approvals once, by design.
- The ×2 heuristic is an estimate, not a tokenizer count; it is deliberately conservative for Cyrillic (≈2 bytes per token) but unproven for other scripts – the final backstop is the server's overflow rejection, not the estimate.
- `verify_no_truncation` currently protects only the experimental graph provider's model construction; the default `personal_memory` path relies on the layered checks above and on Ollama 0.40+ behaving (open question below).

## Open questions for the product owner

– Считается ли 8k-уровень бюджетов (3000/4000 байт, `local_app/personal_memory_contract.py:18`) поддерживаемой конфигурацией? Практика показывает 413/502 на полном цикле чата при `LOCAL_CONTEXT_TOKENS=8192`; следует ли при `personal_memory_enabled=1` проверять минимум 16384 при старте приложения, чтобы ошибка ловилась на запуске, а не в чате?

– Эвристика «(context_tokens – max_output_tokens) × 2 байта» – оценка, а не токенайзер (`local_app/runtime.py:92-95`). Достаточно ли её для не-кириллических текстов, или нужен измеренный preflight-счётчик в продуктовом рантайме, как в НИРС (`research_memory/personal_memory_lab/runtime.py:153-174`)?

– Вызов `verify_no_truncation` включён только в экспериментальный personal_graph-провайдер (`local_app/personal_graph_memory.py:916-919`); дефолтный personal_memory-путь полагается на `truncate=False` и отказ Ollama 0.40+. Проверять ли сервер одним probe при старте приложения, чтобы обнаружить откат версии Ollama или форк, молча обрезающий промпт?

– Достаточны ли бюджеты 12000/24000 байт для реальных занятий (замер фактического `prompt_eval_count` в чате сейчас не ведётся), или нужен сбор этой метрики, чтобы обосновать следующие значения бюджетов?
