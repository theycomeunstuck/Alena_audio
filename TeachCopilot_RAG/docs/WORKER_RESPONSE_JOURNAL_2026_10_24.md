# Локальный журнал ответов worker

Продолжение исправления опроса PostgreSQL из `WORKER_DB_RECOVERY_2026_10_23.md`.
Полученный ответ runtime теперь фиксируется в отдельной SQLite БД до разбора
содержимого и завершения задания в PostgreSQL. Потеря PostgreSQL после получения
ответа больше не оставляет единственную копию в `MemoryWorker.calls`.

## Порядок и восстановление

1. Worker проверяет аренду задания и фиксирует локальную подготовку вызова.
2. PostgreSQL сохраняет штатный маркер начала вызова.
3. Runtime вызывается один раз.
4. Локальный журнал фиксирует возвращённый объект или `raw_response` исключения.
5. Worker проверяет ответ и сохраняет результат задания в PostgreSQL.

SQLite использует `synchronous=FULL`, короткие транзакции и отдельные соединения.
Строки вызова и результата неизменяемы; повторная запись другого результата
отклоняется. Несколько worker могут использовать один файл. Подготовленная строка
без результата не доказывает отправку запроса или отсутствие ответа.

Журнал хранит ID задания и worker, назначение и номер вызова, время, необработанный
объект runtime, тип исключения и хеш конфигурации БД. Полные запросы, DSN, имя
пользователя и пароль подключения в него не записываются. Сам ответ может содержать
частные учебные сведения, поэтому журнал остаётся локальным в `.local/` и не входит
в HTTP, ученический архив или Git. Это объект после возврата runtime, не исходные
HTTP-байты провайдера.

Настройка `LOCAL_MEMORY_RESPONSE_JOURNAL` задаёт файл; по умолчанию используется
`.local/memory-worker-responses.sqlite3`. Пустое значение не выключает защиту.
Нужны явно заданные host или hostaddr и dbname. Порт нормализуется с учётом PGPORT,
адрес – с учётом PGHOSTADDR. DSN или окружение с PGSERVICE отклоняются, поскольку
служебный файл может неявно менять сервер. Учётные данные не влияют на отпечаток.
Чужая SQLite БД не используется и не преобразуется в журнал.

При отказе локального журнала worker завершает работу с кодом 1 без повторного
вызова. При отказе PostgreSQL сохраняется прежняя семантика аренды и
`unknown_outcome`; журнал не завершает задание и не создаёт версию памяти вместо
БД. Автоматического импорта, повторной генерации и удаления записей нет.

## Чтение без PostgreSQL

Команда использует текущую конфигурацию БД только для отпечатка и не соединяется
ни с PostgreSQL, ни с моделью:

```powershell
.venv-local/Scripts/python.exe scripts/inspect_memory_responses.py --job-id JOB_ID
.venv-local/Scripts/python.exe scripts/inspect_memory_responses.py --call-id CALL_ID --include-response
```

Без `--include-response` вывод содержит только метаданные. Внутренний
`calls[].response_journal_id` связывает диагностику задания с локальной записью.
Просмотр не меняет статус задания. Неизвестный исход сохраняется до отдельного
решения оператора; сохранённый текст сам по себе не подтверждает смысл или качество.

## Границы проверки

Тесты используют синтетические ответы, отдельные временные SQLite и PostgreSQL БД.
Проверяются потеря подтверждения до и после фиксации результата PostgreSQL,
аварийное завершение процесса после локальной фиксации, параллельные писатели,
обрезанный и невалидный ответ, отказ журнала до вызова и после ответа, изоляция БД,
сохранность чужого файла и чтение без доступной PostgreSQL. Настоящих генераций,
embeddings и оплачиваемых запросов нет.

Итоговая целевая регрессия – 72 пройденных теста. Полный
`scripts/verify_local.py --ui` после исправлений – 1610 pytest-тестов и 52 проверки
карточки, без пропусков, включая браузер. Логи сохранены отдельно в
`.local/product_followup_20261024/response_journal01/full01/`, предыдущий отчёт –
в `prior_verification/`. Независимый агентский просмотр завершён; замечания о
чужом SQLite файле, Unicode и идентификации БД устранены. Это проверка программы
на синтетических данных, не человеческая содержательная экспертиза.

Сохранность зависит от успешного локального commit. Завершение процесса до этого
commit, одновременный отказ локального носителя или ответ, не возвращённый runtime,
по-прежнему могут оставить только неизвестный исход. Журнал не устраняет эти случаи.
Рабочие процессы не перезапускались; новое поведение начнёт действовать после
обычного обновления worker. Исходные исследовательские результаты и журналы не менялись.
